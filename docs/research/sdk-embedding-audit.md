# RAI-115: аудит границы embedding SDK

Дата: 2026-10-12. Baseline: 3a60f93a2197a0097e4a9f326260dd9fd7844578. Worktree: lane/rai-115-sdk-audit; исходное дерево чистое. Это read-only аудит исходников и проектирование решений. API, runtime tests и реальные provider calls не выполнялись.

## Вывод

Минимальный SDK можно собрать поверх текущих core/runtime/dsl/providers, сохранив единый runtime. Главный разрыв — нет host-facing launcher/resource factory, который связывает typed Program с backend, jobs, scopes, admission, budget и tools, задаёт root и управляет ресурсами в ZIO lifecycle. Typed composition существует; удобный launch сейчас привязан к REPL, а CLI обслуживает отдельный process-oriented путь.

Рекомендация для отдельного ADR: явный ZIO-native managed runtime capability над текущим AgentLoop/JobManager/Admission/BudgetLedger. Host создаёт и закрывает его в своём scope; SDK не вводит второй loop/scheduler. Task с environment Any можно сохранить в первом additive срезе и передавать зависимости явно. ZLayer.scoped можно рассмотреть как adapter, но форма API остаётся решением ADR.

Подтверждённое позиционирование: главное отличие — максимально удобный Scala DSL для AI-native SDLC. Первый путь — Scala 3 workflow через local generic runner; CI system пока не выбран, GitHub Actions не первый target. Целевой проект — соседний TokenRouter/Yabanin: работа с его кодом только отдельными companion cards; эта Raider card не меняет и не исследует sibling repo. Желаемый цикл включает PR, auto commit/merge, version/changelog/tag и build artifacts, но deploy исключён. Release tag создаётся локально: push tag исключён, так как он запускает GHCR publish и staging deploy в целевой системе. Forge/remote adapter ещё не выбран. Human gates конфигурируются в Scala workflow. Host embedding — дополнительная SDK proof. Raider wave продолжается, проект OSS. Experimental preview до M4 допустим с migration для breaking changes; TASTy limitation указывается честно. Durable resume не требуется: после interruption result uncertain, rerun явный. Расширенная trace privacy deferred; preview рассчитан на trusted local data.

## Lifecycle invariants и варианты

Официальные документы ZIO описывают Scope как базу управления ресурсами, а ZIO.acquireRelease/ZIO.scoped/ZLayer.scoped — как способы привязать release к lifecycle ([Scope](https://zio.dev/reference/resource/scope/), [ZLayer](https://zio.dev/reference/contextual/zlayer/)). Это поддерживает ZIO-native lifecycle, но не утверждает форму Raider API.

- Один execution instance: root, validated limits, admission+ledger, frozen tool/config snapshot и явный owner. Shutdown сообщает incomplete/uncertain cleanup; upstream cancellation acknowledgement не обещается.
- maxLLM=1: parent join не удерживает модельный permit; проверить на публичном host path.
- Cost claims: перепровести UsageObserved → loop outcome → withSlot settlement → UsageReport. Из текущего кода success AgentLoop path записывает zero; unknown price должен остаться unknown/unpriced, не стать zero. Hard cap зависит от reservation estimate и pricing policy, не только от ledger.
- Два host instance изолируют jobs, roots, queue, budget и tools; закрытие одного не влияет на другой.
- Construction не выполняет network call/dispatch.
- Task[Any,...] не принимает host services через R. Возможны явный dependency capture при создании Program или изменение контрактного environment типа. Рекомендуется сначала минимальный вариант с явными dependencies; generic effects потребуют отдельного обоснования.
- ZIO Scope ownership отличается от текущего JobManager daemon ownership; ADR должен определить acquisition, close grace и report.

Для ADR оцениваются четыре boundary:

1. **Рекомендуемый managed runtime capability:** effectful construction явных backend/config/tools/policy/limits; host scope управляет закрытием; capability запускает Program и jobs. Переиспользует один runtime graph. Риск — согласовать manager-owned daemon fibers и cleanup report.
2. **ZLayer-first:** естественно в ZIO app graph; может быть тонким adapter. Риск — навязать layer API и усложнить несколько isolated instances.
3. **Низкоуровневые AgentLoop/Admission/JobManager:** доступно и мало новых abstraction, но consumer соединяет internals и lifecycle вручную. Не достаточно как единственный SDK.
4. **REPL/CLI reuse:** не primary API из-за Runtime.default/global registries или process-specific schemas/coding defaults.

ADR выбирает package/artifact boundary; Program vs Agent/Workflow entry; backend injection vs direct provider factories; generic ToolRegistry vs optional coding tools; scope/close/uncertainty behavior; root/instance isolation; Task environment policy; Scala/ZIO/JDK compatibility; credentials; bundle admission boundary; API compatibility/deprecation. Ни одна signature не принимается данным audit.

## Вопросы, требующие решения владельца

Уже подтверждено: Scala DSL for AI-native SDLC — primary differentiation; Scala workflow через local generic runner first, CI system TBD (не GitHub Actions first); TokenRouter/Yabanin target, sibling work отдельными cards; desired cycle PR/commit/merge/version/changelog/tag/artifacts без deploy; release tag local-only, no push; human gates configurable; preview pre-M4 on pinned toolchain with migration for breaking changes; no durable resume (interrupted/unknown + explicit rerun); extended trace privacy deferred, trusted local data; Raider wave continues, OSS only.

1. Нужен ли ZLayer entry в preview или достаточно explicit runtime capability из обычного ZIO effect?
2. Основная единица authoring: любой Program, Agent/Workflow profile или composable typed stages/checks/approvals? Что generic Raider DSL, а что TokenRouter kit?
3. Принимать готовый ModelBackend, предлагать factories для OpenAI/Anthropic или оба пути?
4. Оставить generic ToolRegistry основным, а coding tools optional dependency с явной workspace/policy?
5. Нужен ли early public registry publish? План предполагает local packaged consumer первым.
6. Первая preview использует pinned Scala 3.9.0/ZIO 2.1.26, cross-build сейчас не нужен. Достаточно ли заявить Scala 3.9+ compile consumption после consumer test, с указанием, что backward consumption compiler-ами до 3.9 не обещано?
7. Кто может пройти внешний workflow/CI trial и в какой срок? Участники/даты пока не подтверждены.
8. Какие TokenRouter SDLC stages/checks/output schemas обязательны для первого cycle? High-level cycle подтверждён, precise mapping нужен.
9. Как определить forge-independent PR contract и local generic runner semantics до выбора CI/forge adapter?
10. Кто задаёт trusted policy, target branch, protected paths и проверки PR/commit/merge/version/tag? Как обрабатывать неоднозначную Git mutation?
11. Нужна ли compile/plan preview до model dispatch или более широкий preview?
12. Какие локальные event/artifact data нужны, учитывая deferred trace privacy?
13. Gross envelope 120–240h — planning estimate до deduplication; SDLC kit и remote forge adapter unknown. Coordinator должен вывести actual remaining из work records/board. Подходит как planning рамка?

Ответы 1–6 и 8–12 меняют API/product acceptance и должны попасть в соответствующие ADR; до них не фиксировать signatures, reusable stages или integration policy. 7 и 13 могут оставаться pending. Независимую workflow consumer acceptance можно готовить параллельно.
