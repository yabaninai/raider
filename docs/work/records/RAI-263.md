## Resulting behavior

The REPL facade `Chat` (in `modules/repl/src/main/scala/raider/repl/facade/FacadeOps.scala`) now implements the working-product §4 W11 golden scenario as real semantics (decision side (a), recorded in `docs/adr/ADR-040-chat-close-lifecycle.md`):

- `chat.close()` is idempotent and multi-closer-safe (AtomicInteger lifecycle `0` open → `1` closing → `2` closed/sealed; transitions CASed under `closeMonitor`; the in-flight fiber set is read/mutated only under `turnLock`). It interrupts the chat's own in-flight turn fibers and then seals the chat; it never touches session jobs, their steering mailboxes, or receipts (chat-scoped close).
- An `ask` racing a close resolves exactly once: a turn that completed before the interrupt landed keeps its user+assistant pair in the history and returns the reply (completion wins); a turn the interrupt reached surfaces a typed `RaiderError.Cancelled` with no fabricated reply. The reply pair is appended to the history ON the turn fiber before any Exit observer, so a closing race can never drop a settled reply; earlier history is never erased.
- `ask` on a closing/closed chat refuses typed with `RaiderError.InputValidation("chat is closed: close() was already called; open a new chat with openSession(...)")` (RA-INP family; no core error member added) before any dispatch. This refusal is a chat-turn property only (ADR-040 §3.3/§3.4): `Chat` has no `start` member, and `AgentRef.start` session jobs are deliberately unaffected — jobs keep running and their receipts settle (CHAT-04).
- Session-job interplay is unchanged by a chat close: a queued steering receipt still resolves `Applied` at the next turn boundary (or expired when the job goes terminal per RAI-132 conservation), and a concurrent job cancel settles `Cancelled` independently; both are bounded.

Evidence layer added: unit spec `ChatCloseSpec` (7 tests: golden, in-flight close, completion wins, close-vs-completion race XOR, chat-scoped job untouched, close+cancel concurrent, concurrent closers) on the real loop with a scripted gate backend (all concurrency awaits bounded by 10 s live-clock timeouts; suite is `@@ TestAspect.sequential` because `FacadeOps.steer/owners/started` registries are keyed by `JobId` and zio-test runs tests in parallel — two suites would otherwise collide on `JobId("j_1")`), and installed-PTY spec `InstalledChatClosePtySpec` driving the unpacked distribution launcher over `/usr/bin/script` with the real scala3-repl compiler and the mock provider through the golden sequence (ask → reply in history → close twice → history preserved → post-close ask caught typed `RaiderError.InputValidation` → exactly one answer in the transcript → `:quit` exit 0).

## Limitations / blockers

- During development two `testOnly` runs hung (unbounded test barriers before the diagnosis); they were terminated by exact PID (sbt 67584, forked test JVM 67660, CWDs verified inside this worktree). Root causes found and fixed in the SPEC (not the product): (1) the fixture session needs `BudgetLimits.make(maxConcurrentLlm = 2)` — the product default of 1 serializes a chat turn behind a parked job turn (correct product behavior; the test needed both parked at once); (2) the suite needs `@@ TestAspect.sequential` — parallel zio-test tests collide on `JobId("j_1")` in the facade-wide `steer/owners/started` registries; (3) acceptance assertions must read steering msg ids from the receipt (facade-wide `nextSteerId` counter), not literals. Temporary `println` instrumentation used for the drain diagnosis was fully removed; the final `FacadeOps` diff contains no debug code (`git diff` inspected).
- Close boundedness is interrupt-based (no wall-clock timeout parameter); ADR-040 §6 records this as a non-goal.
- The PTY transcript artifact lives under gitignored `modules/repl/target/rai263-pty/` (regenerated by the spec on every run), consistent with the RAI-262 precedent.
- No real paid provider was called; the PTY evidence uses `RAIDER_PROVIDER=mock` (scripted fixture).
