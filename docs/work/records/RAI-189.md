## Resulting behavior

The ordinary REPL facade now wraps each tool stamped `RecoveryClass.Mutating` at the `AgentLoop.runText` construction point. The typed `ToolApprovalHook` receives the invocation name, frozen recovery class, arguments, and a per-request token. An explicit `Approve` invokes the original tool; `Deny` and an absent hook fail closed with `RaiderError.ToolDenied` (`RA-TOOLDENY`). Read-only and idempotent tools are not prompted. In chat mode the existing `ChatLayoutSink` waits for the shell input loop to submit the exact displayed token using `:approve <token>` or `:deny <token>`; duplicate/stale tokens do not settle a request. The launcher's frozen registry is not expanded.

Tool cards remain bounded and render through the existing renderer bridge. The approval wait uses the shell's existing JLine input/read loop and render writer.

## Final-round disposition (2026-10-24)

The requested CLI ChatLoop wiring was not implemented. `raider-cli` does not depend on `raider-repl` (`build.sbt:160-165`), while `raider-repl` depends on `raider-cli` (`build.sbt:109-129`); the existing typed `ToolApprovalHook`, context, and decision are declared in `raider.repl.facade.ReplSession` (`modules/repl/src/main/scala/raider/repl/facade/ReplSession.scala:37-54`). Consequently the CLI cannot reuse that hook or the REPL facade's `approvalTools` implementation (`FacadeOps.scala:206-246`) without moving the shared API/helper across the module boundary or introducing a dependency cycle. The build file is coordinator-owned, the card does not authorize a public contract change without an ADR, and this lane did not make either change. Duplicating a CLI-specific approval protocol would violate the assignment's reuse requirement.

The three requested PTY transcripts and ×3 repetitions were not run: the CLI path has no approval edge to exercise, and presenting REPL-only transcripts as CLI acceptance would be misleading. P2W draft-preservation/single-writer behavior during approval therefore remains unverified for this acceptance. No quality gates or manifests were run in this final round because there was no product-code change; the previously recorded change-classification-only `make quality-changed` remains non-execution evidence. No verify command was run. RAI-189 remains blocked and is not review-ready until the coordinator resolves shared hook ownership/API placement and assigns the corresponding integration/gate work.
