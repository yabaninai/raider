# RAI-260: Structured multi-file and delete mutation tools for the native coder

Status: done. Date: 2026-11-01T20:14:38Z. Baseline commit/source: `964a388` (branch `lane/rai-260`, worktree `artifacts/lanes/rai-260`).

## Resulting behavior

The coder toolset (`CodingToolset`) exposes two additional structured mutation tools, registered after the six coding tools and before the opt-in state tools:

- `fs_patch_multi {"diff","expected_sha256":{path→sha}}` — applies a multi-file git-style diff ALL-OR-NOTHING via the existing RAI-067 `PatchTool.applyAll` engine. Validation runs against every file's current SHA-256 before anything is written; the whole staged apply (validation + commit) runs in ONE uninterruptible region (`ZIO.uninterruptible`), so a cancelled caller is deferred to the tool boundary and the workspace is left either pristine or fully applied. The tool feedback is a single-line JSON report `{applied:[…],failed:[{file,code,reason}],rolledBack,staged:[…]}`.
- `fs_delete {"path","expected_sha256"}` — new `DeleteTool` (package `raider.tools.files.edit`, reusing the `private[edit]` EditTool helpers) deletes exactly ONE regular file by atomic POSIX unlink. Missing file → typed `RA-INP` naming the path with nothing deleted; directory target → typed `RA-INP` refusal; stale provenance → typed `RA-TOOLDENY` (`STALE DELETE: …`) with the file surviving; workspace escape → typed `RA-TOOLDENY`; oversized file → `RA-INP`. Report: `{action:"deleted",path,old_sha256,bytes}`.

Both tools carry frozen `RecoveryClass.Mutating` stamps and `concurrentSafe = false`, so plan-mode read-only enforcement excludes them from the advertised surface and denies direct calls (`RA-TOOLDENY`, nothing executed) exactly like `fs_edit`/`fs_patch`.

**Atomicity decision (card deliverable).** Rollback, not staged-apply-with-disclosure: the RAI-067 engine validates all files first (nothing written on any validation failure — `rolledBack=true`, per-file typed reasons, `staged` names the computed-but-discarded files) and, on a commit-phase I/O fault, performs a best-effort IN-MEMORY restore of already-applied files (`rolledBack=true`, failure reason `commit failed for <path>: …; all applied changes were restored`). An incomplete restore is reported honestly as `rolledBack=false` with a `ToolOutcomeUncertain` entry — the caller must inspect the workspace. There is NO journal: durability across JVM crash / `kill -9` mid-commit is NOT covered and is not claimed (trust-boundary rule: no exactly-once/durable-resume claims for arbitrary write sequences).

**Serialization contract (cancellation/concurrency acceptance).** `CodingToolset.make` creates one `zio.Semaphore(1)`; `fs_edit`, `fs_patch`, `fs_patch_multi` and `fs_delete` serialize on it. Parallel tool calls — including parallel delegated children, which share the parent's registry instance — cannot interleave read-validate-write phases on shared files; a call racing another writer on the same file fails CLOSED with a typed stale-provenance denial instead of silently merging. Process-local guarantee only.

**Registry pin update.** `TOOLRC-01` / `STW-01` / `STW-03` now pin the explicit sorted 8-element coding list `CodingNames = List("fs_delete","fs_edit","fs_patch","fs_patch_multi","fs_read","fs_search","fs_tree","proc_run")` (with state tools appended: 12). The `RecoveryTaxonomy` consistency test intentionally still iterates the frozen six-name set (see Limitations).

**Spec-placement note.** The delegation test lives at `modules/tools/src/test/scala/raider/runtime/delegate/DelegationMutationToolsSpec.scala` (package `raider.runtime.delegate`): `modules/runtime` does not depend on `raiderTools` (the dependency direction is tools → runtime, and `build.sbt` is coordinator-owned), so a runtime-module test cannot construct the real `CodingToolset`. Placement inside the tools module keeps both the real toolset and the real `DelegationToolset` on one classpath; the path is within the card's allowed `modules/tools/src/test/**`.

## Limitations / blockers

- **`RecoveryTaxonomy` gap (disclosed).** The canonical taxonomy predates `fs_patch_multi`/`fs_delete` and classifies unknown names as ReadOnly until a separate lineage card extends it. The operative policy stamps here are `Mutating` (this is what `AgentLoop.enforceReadOnly` consumes), and the taxonomy-consistency test intentionally still iterates the frozen six-name set. Follow-up card required for full lineage closure.
- **No crash durability.** `fs_patch_multi` restore is in-memory best-effort; a JVM crash mid-commit is outside the contract (see Atomicity decision). Cancel-deferral is the covered guarantee.
- ZIO Test evaluates `assertTrue` thunks after the test scope closes (the tmp workspace is already deleted), so all disk-state assertions in the new specs are captured into eager vals before asserting. This harness subtlety is documented in the spec source; it cost one debugging round-trip (6 tests initially read disk lazily and failed after cleanup).
