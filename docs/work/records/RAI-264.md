## Resulting behavior

`docs/parallel-development.md` gains **§1d "Lane build hygiene: JDK/toolchain pin for lanes and gates (RAI-264)"** — a sibling of RAI-250's §1c, same style (measured source, recognition, what-NOT-to-do, concurrency guidance), no restructuring of existing sections. The section records:

1. **The pin (required):** every lane shell and every gate run executes sbt under JDK 21 (`export JAVA_HOME=/Library/Java/JavaVirtualMachines/jdk-21.jdk/Contents/Home` plus `PATH="$JAVA_HOME/bin:$PATH"`). Homebrew `openjdk` on this host is currently JDK 27, and an unset `JAVA_HOME` lets the sbt launcher resolve it even when PATH `java` is 21 — evidenced by the failed RAI-254 run whose manifest `toolchain.java` recorded Oracle `21.0.12.1` while its sbt banner read `welcome to sbt 1.11.4 (Homebrew Java 27)`; verify the sbt banner, not `java -version` alone.
2. **Recognition, verbatim:** a cold `raiderCli / Test` compile under JDK 27 fails deterministically in dotc 3.9.0 parsing JDK 27's `java.lang.invoke.VarHandle` classfile (LazyVals pulls `VarHandle` from the JRT). The section quotes the crash block verbatim from the failed manifest's `sbt-test.log`: `java.lang.AssertionError: assertion failed: failure to resolve inner class:` / `externalName = java.lang.invoke.VarHandleDoubles$FieldStaticReadOnly` / `while parsing /modules/java.base/java/lang/invoke/VarHandle.class`, with the `ClassfileParser$innerClasses$.classSymbol` → `LazyVals` frames. Evidence pair cited: manifest `20261101-044235-92625-0001` (failed, Homebrew Java 27) vs `20261101-044855-95050-0001` (same fingerprint passed under the JDK 21 pin: 5 checks, 1722 tests / 0 failed / 0 ignored, banner `Oracle Corporation Java 21.0.12.1`), both from the RAI-254 record (`wt/rai-254`).
3. **Distinct from the §1c zinc poison** (card contract): a contrast table keyed on signature / carrier / clean-heals / remedy. For the zinc E008 marker (`value id is not a member of raider.core.ToolCall` at `AgentLoop.scala:772:7`) `sbt --batch raiderCore/clean` heals (57–65 s; retry never heals 6/6 and incremental recompilation does not heal — `docs/research/zinc-concurrency-2026-10-28.md` §12). For the JDK 27 dotc crash a clean does **NOT** heal — a clean recompile under JDK 27 re-crashes deterministically; the remedy is pinning JDK 21, not cleaning. The zinc study's clean-heals logic explicitly does not transfer: nothing is poisoned, the compiler/JDK pair is wrong.
4. **What NOT to do, and why:** no clean+retry loops under JDK 27 (burns a full compile, same AssertionError); no §1c heal / zinc diagnosis / product-defect card for this marker (E008 absent, no zinc state corrupted); no reading of a green warm-zinc JDK 27 run as JDK-27-safe (RAI-254's fixup manifest `20261101-053427-13638-0001` passed under Homebrew Java 27 only because zinc was warm); no lane-side dotc/Scala upgrade or `build.sbt` hard pin (coordinator-owned shared build, separate card — card non-goal).
5. **Mixed JDKs on one host (concurrency acceptance):** zinc state is copy-local, so a JDK 27 lane crashes only its own copy; pin per shell before the first sbt call (an unpinned start crashes even among pinned-green siblings, and not vice versa); do not run §1c's `raiderCore/clean` on a sibling's behalf for this marker; the pin does not remove §1c's ~12% E008 overlap risk under JDK 21 — both hygiene rules coexist; treat one dotc crash in a wave as the expected unpinned-start case, check the sbt banner first.

No gate-policy, registry, build, or product changes; no changes to §1–§1c or any other section.
