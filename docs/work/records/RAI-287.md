## Resulting behavior

The three W17 gaps are closed on the candidate fingerprint:

1. Deterministic LOCAL Yabanin gateway contract stand (fixture): serves the
   ACCEPTED gateway wire only — POST `<base>/chat/completions` with Bearer
   child-credential enforcement (gateway-style 401/403 JSON error bodies,
   per-response usage objects, a full tool round via `tool_calls`) plus GET
   `<base>/models` (liveness). Loopback, ephemeral port, per-test
   acquire/release ownership, thread-safe request log (method/path/auth/
   X-Yabanin-*/raw body). No session minting, no accounting endpoints: any
   foreign request lands in the log and fails the contract.
2. Candidate gateway integration checks:
   - transport layer (`raider.provider.chat.gateway.GatewayWireContractSpec`,
     C1–C5): gateway base URL used VERBATIM (trailing slash trimmed, no
     `/models` probe); wrong child credential → typed `RA-AUTH` first-shot
     with the key value absent from the detail; `RAIDER_OPENAI_EXTRA_HEADERS`
     (e.g. `X-Yabanin-Labels`) lands on the wire with the value verbatim
     (name case-insensitive per RFC 9110; the JDK server view normalizes
     names) and never carries the credential; a FULL tool round over the
     gateway shows ONLY `/chat/completions` calls — Raider mints nothing
     (exactly one lifecycle owner exists, the wrapper); gateway 403 policy
     refusal → the same typed `RA-AUTH`.
   - runner level (`raider.cli.run.GatewayRunnerAcceptanceSpec`, R1–R5),
     through the real public entry (`HeadlessRunner.run` with an injected
     env map, real `ProviderBackend` → `AgentLoop`): happy path rides one
     verbatim completions call with honest unpriced usage; **explicit
     no-hidden-fallback acceptance**: gateway 401 (auth) / 403 (policy) and
     unreachable gateway all produce the typed refusal (`RA-AUTH` /
     `RA-UNAVAIL`, exit code 20, `status=Failed`, no output) with ZERO
     direct-transport calls — asserted on a second ARMED OpenAI-compatible
     stand whose request log stays EMPTY; concurrency leg (RUN-03): two
     parallel invocations, each its own stand/port/out-dir, no cross-talk.
3. Minimal product seam (only production change): `OpenAIChatBackend` gains
   `make(config, env: Map[String, String])` and `extraHeaders(env)`; the
   public `make(config)` overload is unchanged and resolves `sys.env` at
   construction, so the wire and error mapping are identical in production.
   This lets the label-attribution check pin the header source hermetically
   without mutating the process environment.

## Limitations / blockers

- The gateway stand fixture is duplicated in two modules (path constraint:
  `build.sbt` not modifiable under this card). A coordinator-owned build
  change could later share one fixture; not requested.
- The two-arg `make` snapshots the header environment at backend
  construction; production previously read `RAIDER_OPENAI_EXTRA_HEADERS`
  per request from `sys.env`. Equivalent for the runner (one backend per
  run) and documented at the seam; flagged for review.
- Label header NAME is asserted case-insensitively (RFC 9110; the JDK
  server normalizes names); the VALUE is asserted verbatim.
- Non-streaming only: the streaming backend has no env-header mechanism;
  gateway SSE coverage remains with the streaming transport card (RAI-012
  line), consistent with the gateway baseline's non-streaming MVP scope.
- The concurrency leg is a 2-invocation ownership/isolation check, not a
  load test.
- No live gateway or paid calls were made (offline-first policy); live-wire
  parity rests on the RAI-184 record and the deterministic stand.
