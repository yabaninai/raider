## Resulting behavior

`:type <expression>` в продуктовом REPL-цикле (`raider.repl.Main`, no-flag
legacy mode) печатает точный тип выражения через РЕАЛЬНЫЙ
interpreter-компилятор БЕЗ исполнения:

- `Commands.handle(":type …")` форвардит строку verbatim (trim) в
  `engine.eval` — dotty ReplDriver 3.9.0 сам разбирает СВОЮ нативную команду
  `:type` (`ParseResult.TypeOf` → `ReplCompiler.typeOf`): выражение
  компилируется против живого состояния сессии и не запускается. Никаких
  эффектов, модельных вызовов, мутации биндингов; resN-нумерация не
  сдвигается (pinned тестом). Готовый typeOf-механизм scala3-интерпретатора —
  кастомного парсера/форматтера нет.
- Ошибка типизации — честный диагност компилятора (E006 `Not found: …`, E007
  `Found:/Required:`); REPL жив, следующий запрос работает. Пустой ввод —
  usage самого драйвера `:type <expression>`.
- Multiline: `:type`-строки идут через тот же pending-buffer путь, что и
  Scala-ввод; при подаче буфер сплющивается в однострочный источник
  (`Commands.typeQuerySource`: `\n`→пробел + trim — CommandExtract-regex
  драйвера full-matches одну строку). Residue задокументирован: стейтменты
  блока требуют явных `;` после флюшения (иначе честная syntax error).
- Регистрация: `Commands.helpText` получил командную строку
  `:type <expression>`; stale-строка «Not in this slice» приведена к
  актуальной (`:type` выпал; completion/live providers уже в продукте);
  `ReplChatCommands.catalog` — запись `:type` в helpText-порядке. Freshness
  equality (ReplChatPaletteSpec, прецедент RAI-111) зелёный. Механика
  TAB-completion/palette не тронута (выводятся из реестра).
- Модуль chat (JLine) не затронут; компилятор-слой `modules/repl-engine`
  только потребляется (frozen `ReplEngine.eval`).
