## Resulting behavior

The "Workspace tools" section of `docs/api.md` no longer claims that
`CodingToolset.make(workspaceRoot)` "wires six tools" — the stale Phase 4.3
wording left untouched by RAI-260 and flagged by the RAI-270 review. It now
documents the full live coding-tool surface, cross-checked against the live
`CodingToolset` registry and the refreshed RAI-270 `CoderBasePrompt`:

- **Eight coding tools named as the registry wires them:** `fs_read`,
  `fs_search`, `proc_run`, `fs_edit`, `fs_patch`, `fs_tree`, `fs_patch_multi`,
  `fs_delete` (the RAI-260 additions included), with the opt-in `state_*`
  tools (RAI-094) noted as appended only when a `StateStore` is supplied.
- **New `fs_patch_multi` table row:** `diff`, `expected_sha256` (map of path
  to current SHA-256); multi-file git-style diff (new, modified, and deleted
  file sections); all-or-nothing — every listed file is validated against its
  current SHA-256 before anything is written, and any failed check applies
  nothing (matches `PatchTool.applyAll`'s uninterruptible staged apply).
- **New `fs_delete` table row:** `path`, `expected_sha256`; deletes exactly
  one regular file, directories are refused, irreversible — there is no undo;
  a stale hash is a typed denial and nothing is deleted (matches `DeleteTool`).
- **New sentence on the RAI-260 serialization contract:** the four structured
  file mutation tools (`fs_edit`, `fs_patch`, `fs_patch_multi`, `fs_delete`)
  serialize on one per-toolset lock; a writer racing another writer on the
  same file fails closed with a stale-provenance denial instead of silently
  merging.

The two new rows sit after `fs_patch`, keeping the mutating file tools grouped
in the RAI-270 prompt's order. The pre-existing six rows and the trailing
`parsed`-output paragraph are untouched. Documentation-only: no code, prompt,
registry, or gate-policy change; no new API documentation beyond the coder
tool-surface section.
