## Resulting behavior

`LineageRenderer.render` (ADR-031 renderer card) now emits, per node, REAL
composition over the projection runtime instead of `//` comments and `()`
bodies:

- Model/tool nodes emit `LineageStep.model`/`LineageStep.tool` calls with the
  `dataRef` KEY only (`// data:` comment retained) inside a value-threaded
  `flatMap` chain: every step's report is bound (`n_<id>` variables, deduped
  per scope) and an in-scope dependency id is passed as the bound value
  (`Vector(n_m1.head.id)`); cross-scope dependency ids render as id literals
  (deep-tree `n3` → `n1`). Sequencing = child order (pre-order chain).
- Delegations/phases become named object members building sub-Programs —
  emitted as `val <name>: Program[Unit, Vector[StepReport]] =
  Program.fromFunction("<name>") { _ => ... }` (the review-approved PRC-02
  fixture shape: a `def` with an empty parameter list cannot be applied as
  `<name>(())`; a val is spliced via `Program.apply(())`). Members are
  emitted in pre-order discovery order; a def's own node step lives INSIDE
  its body (nesting = scope depth + 1), so a childless member still has one
  real statement and a recorded failure short-circuits from within the
  sub-Program.
- Recorded-failed nodes emit `LineageStep.failed(id, NodeKind..., dataRef,
  inputs, nesting, reason = "recorded outcome: <class>")` — `Task.fail`
  typed (RA-OUT channel, `LineageStepFailure` cause), short-circuiting the
  chain.
- The object exposes `val program: Program[Unit, Vector[StepReport]]` — the
  single entry point for executed-projection acceptance (RAI-142: `Task.zio`
  on `lineage_x.program(())`).
- The generated file carries the ADR-031 §2.1 mandatory statement that it is
  a dry-run description dispatching nothing and is NOT a replay/rerun
  entrypoint.
- Byte-identical determinism preserved (LIN2-C-01: repeat renders identical;
  LIN2-C-03: concurrent renders isolated — all renderer state is local to the
  invocation). Unknown node kinds stay typed-rejected (LIN2-02); a NEW
  defensive rejection covers unknown recorded outcome classes.
- The pre-RAI-141 indentation-region machinery (comment-only bodies, `()`
  closers, `firstDefIndent`) is deleted: comment-only bodies are structurally
  impossible.

## Failed-node source decision (pinned)

**Graph field.** The renderer detects a recorded-failed node through
`NodeView.outcome: Option[String]` (new defaulted field) — the node's
RECORDED OUTCOME CLASS surfaced by the view adapter from the graph, in the
frozen lineage-data v1 vocabulary (`"Succeeded"` / `"Failed"` /
`"Cancelled"` / `"Timeout"`), `None` when the graph carries no outcome.

Justification: ADR-031 §2.1 pins the rendering layer's data source to the
graph model (`LineageView`) only — the renderer never reads
`lineage-data.json`, so a data-derived source is architecturally impossible
without widening the render API; and the runtime graph already carries the
recorded outcome (wave-1 `SessionNode.ToolCall.outcome`), so surfacing it on
`NodeView` mirrors the §2.6 `inputs` discipline.

Mapping (renderer-side, typed): `None`/`"Succeeded"` → reporting step;
`"Failed"`/`"Cancelled"`/`"Timeout"` → `LineageStep.failed` with the bounded,
payload-free reason phrase `"recorded outcome: <class>"` (ADR-031 §2.5 m1
carve-out sentence added to the ADR; no result tails, no args — payloads stay
addressable by `dataRef` only); any other class → `RenderError.UnknownKind`
(defensive, future wire revisions), never guessed. Every recorded non-success
is treated as an honest short-circuit (the dry run reports structure; a step
that did not succeed fails the chain with its exact outcome class named).

## Limitations / blockers

1. **`SessionGraphView` population is OUTSIDE this card's allowed paths**
   (`modules/cli/src/main/scala/raider/cli/lineage/SessionGraphView.scala` is
   CLI main). The PRODUCT CLI export therefore currently renders projections
   with empty `inputs` and no failed-step markers until the follow-up
   integration card lands. Proposed follow-up (RAI-141.b, one-file card):
   populate `inputs = n.inputs.map(_.value)` and
   `outcome = toolOutcomeClass(t.outcome)` in `SessionGraphView.toView`
   (mirror of the gate's `GraphToView` adapter, verified here); its spec
   expectations then flip to the threaded/failed shapes (the gate spec
   already pins them). ADR-031 §2.6 explicitly assigns this integration work
   to RAI-141's contract; the card's allowed-paths list omits the file.
2. The compile gate keeps its documented test-local `GraphToView` adapter
   (snapshot discrepancy pattern from W10) — now extended to populate
   inputs/outcome, so the gate exercises the POPULATED contract while the
   product adapter does not yet.
3. Cross-scope dataflow dependencies render as id literals (deep-tree
   `n3.inputs = [n1]`); in-scope dependencies thread as bound values. The
   executed semantics (report trees, prefix observability, zero dispatch) are
   RAI-142's acceptance, not this card's.
4. Generated sub-Program members are `val`s, not `def`s (see Resulting
   behavior) — required for `<name>(())` splicing; ADR-031's "named defs"
   wording covers the same structure.
