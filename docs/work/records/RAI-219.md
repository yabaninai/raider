## Resulting behavior

`ChatWorkflowExport.exportTo` now distinguishes the staging-race loss inside `writeStaging` — the exact mirror of the accepted RAI-213 fix in `PortableChatExport`: when `Files.createDirectory(staging)` fails with `FileAlreadyExistsException` (the check-then-create window against a concurrent winner, or an obstruction that appeared after the freshness pre-check), the export refuses typed `CWF-R5` with message prefix `staging claim lost: … refusing WITHOUT deleting it` and does NOT delete the existing staging path. The `NonFatal` catch-all keeps its previous behavior (best-effort cleanup of THIS attempt's own staging only). The `publish` FAEE branch is unchanged (there the staging is this attempt's own; the winner already published the target). Net effect: exactly one concurrent chat export publishes; the loser refuses typed with the winner's in-flight staging intact — the two exports can no longer destroy each other through the shared cleanup path, and no half-published bundle can appear.

The class Scaladoc no longer claims that "concurrent exports to the same target serialize on the fixed staging name"; it now states the fail-fast exclusion discipline (exactly one export claims staging and publishes; the loser's `createDirectory` fails with `FileAlreadyExistsException` and refuses typed WITHOUT deleting the winner's in-flight staging; RAI-219; ADR-033 §6.2/§9.1).

Two tests added in a new spec `raider.dsl.workflow.ChatWorkflowExportSpec` (mirroring the accepted RAI-213 test shapes):

1. Deterministic dangling-symlink pin (no visibility seam; `writeStaging` stays `private`): a dangling symlink at the staging path passes the `Files.exists` freshness pre-check and forces `FileAlreadyExistsException` inside `writeStaging`. Asserts the typed refusal contains `CWF-R5`, `staging claim lost` and `WITHOUT deleting`, the symlink staging is intact afterward, and nothing was published.
2. Latched two-thread race, 30 iterations (`RaceIterations = 30`; latches, not sleeps): two threads released by one `CountDownLatch(1)` run full `exportTo` calls to the same target on a 2-thread pool; per iteration, filesystem facts are captured only after both threads join via `future.get(60, TimeUnit.SECONDS)`: exactly one `Right`, the loser is `Left` with code `RA-INP` and `CWF-R5` in the detail, the parent contains exactly `out` (no staging remnant), `out` contains exactly the three §6.2 artifacts byte-identical to the pure re-render, and the winner's `sourceDigest`/`specDigest` match the pure render.
