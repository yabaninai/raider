## Resulting behavior

Chat `--format portable` export now maps named checks onto launcher-pinned trusted checks instead of refusing by construction:

- **ADR-038** (`docs/adr/ADR-038-chat-check-to-trusted-check-export-mapping.md`, status Proposed) fixes the mapping rule: a named check maps iff `(checkId, registrySnapshot)` **exactly matches** a launcher-pinned trusted check, where the canonical snapshot digest is `checkSnapshot = "sha256:" + lowercaseHex(SHA-256(UTF8((checkId +: argv).mkString("\u0000"))))`. Mapping is all-or-nothing per selection, pure, and deduplicates gate steps preserving first-occurrence order. Any non-match (partial id match with different argv, renamed check, unknown id, advisory check) still refuses `CWF-R3` with no fabrication of argv or policy. Advisory checks are documented as intentionally unmappable (keep the Scala export).
- `PortableChatExport` (dsl): `PortablePinnedCheck(checkId, registrySnapshot)` and `PortableExportTarget(..., checks: List[PortablePinnedCheck])`; public helpers `checkSnapshot`, `mapNamedChecks`, `resolveGateChecks`, `gateStepIds`. `exportTo`/`documentJson` emit one gate step per mapped check (`gate`, `gate-2`, …; input `#/steps/act/output`, outputSchema `gateVerdict`; run sequence `act :: gateIds`); the manifest records the gate as `trusted` plus an additive optional `trustedChecks: [{checkId, registrySnapshot}]` array (1..64). `validateManifest` accepts the optional field with closed-item validation; a check-free manifest has no `trustedChecks` key (backwards compatible).
- `ExportWorkflowCommand` (cli): the portable export target carries the pinned table `List(PortablePinnedCheck(CheckWorkspaceMarker, PortableTrustedRegistry.workspaceMarkerSnapshot))` — the launcher-pinned `workspace-marker-present` check (`/bin/test -f marker.txt`, frozen digest `sha256:0c877972cf59788094e1d7653a1f01f6cd1b6c9108d117d5e069bc6b6bdaba0b`, verified independently by recomputing the digest of `workspace-marker-present\0/bin/test\0-f\0marker.txt`). Refusal lines unchanged in shape (`export refused [RA-INP]: ... CWF-R3 ...`), details explain exact-match semantics without leaking inline argv.
- Contract schema `contracts/workflow-portable/schema/chat-portable-export-manifest-v1.schema.json`: optional `trustedChecks` added (array 1..64, closed items `{checkId, registrySnapshot}`, `additionalProperties: false`), not required.
- `docs/examples/portable-workflows/` intentionally unchanged: per ADR-038 §2.4 the examples are standalone documents without named checks; no stale references to the old refusal-by-construction wording remain (grep verified).

## Limitations / blockers

- One flaky observation in the first full `raiderCli/Test/test` under multi-lane load: `ResumeCommandSpec` and `MultiJobExportSpec` (MJE-NESTED fork-record lineage) each failed once. Both were verified passing at the stashed HEAD and in isolated reruns with my changes, pass in the final full runs and in both green gate `sbt-test` executions, and touch subsystems this card does not modify. Attributed to host contention (load average spikes to ~220 with 5+ lanes running suites concurrently).
- `compile-fixtures` requires the untracked pinned toolchain `artifacts/tools/m2` (gitignored); fresh worktrees must copy it from the root checkout provision per `docs/parallel-development.md` §1a before running the gate (exit-21 condition documented in RAI-207).
- Gate runs on this host are contention-sensitive: two EXECUTE attempts were lost to a saturated machine (one real red on formatting + provisioning inside attempt 1, one verdict-less tool-side kill). The recorded passing runs are the ones bound to the final source fingerprint; the board precedent for contention reruns (authorized rerun after host-side kills) was followed.
- The `trustedChecks` manifest addition is validated by schema and code; live end-to-end coverage beyond the mock-provider stand (real provider transports) is out of scope for this card per the mock/replay trust boundary.
