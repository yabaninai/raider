# AUDIT-20261101-ci: headless, CI, and release readiness

Status: done (read-only audit). Date: 2026-11-01. Audited worktree: `wt/audit-20261101-ci`, branch `audit/20261101-ci`, HEAD `935cc2ff0e3498ff1080aad4d53e9b6ca157a405`. Product baseline named by the audit card: `04f74780891e0e7032bf98b3d1dccac279f32354`.

## Result

Raider has a real JVM headless CLI path, normalized generic/GitHub/GitLab environment contexts, structured run artifacts, stable exit handling, and local child-process acceptance. It is useful as an experimentally validated local component, but the repository does not establish hosted CI/release readiness. RAI-045 (development CI) and RAI-047 (release-candidate acceptance) remain todo; the only checked-in hosted workflows are GitHub workflows, and no GitLab pipeline template or hosted release publication was found.

## Findings and next actions

1. **Development CI is not yet the specified productized gate.** [`.github/workflows/ci.yml`](../../../.github/workflows/ci.yml) runs sbt compile/test/format/scalafix and a small `make quality-changed QUALITY_EXECUTE=1` job. [`.github/workflows/raider-fast.yml`](../../../.github/workflows/raider-fast.yml) runs bootstrap, compile, classification, and execution on `ubuntu-latest`. Neither workflow uploads gate manifests/logs on failure, pins Actions by immutable SHA, or supplies the PR merge-base to the classifier. The `quality` job has no explicit timeout, while the fast workflow has a 30-minute timeout. There is no `.gitlab-ci.yml`. RAI-045 is still `todo` in [`m2-p2.md`](../../tasks/m2-p2.md) and requires actual clean-build manifests, stale-evidence/failure behavior, protected-policy/fork checks, and full/security/CI evidence. **Next:** assign/complete RAI-045 before calling Raider's own development CI ready.

2. **Product-level headless behavior has meaningful local evidence.** RAI-185's real-JVM `FirstCiProcessAcceptanceSpec` used closed stdin/no TTY and recorded generic, GitHub-env, and GitLab-env fixtures producing identical semantic `result.json`; it checked artifact discovery, schemas, manifest coverage and hashes, environment redaction, and exit 21 preflight refusal. RAI-187 added a real deadline run and parent-delivered SIGTERM to a CLI child with a real grandchild; its record reports exit 143, bounded cleanup, persisted `events.jsonl`, and absent final `run.json`/`result.json` as an honest interrupted result. RAI-186/195 later wired trusted-check policy and verdicts through exported-launcher child processes, including advisory/blocking exits and artifact-write/signal behavior. The early RAI-186 record header still says “partial,” but the later completion sections, the RAI-195/207 records, and current task/board status supersede that historical snapshot; do not cite its early partial state as current.

   These are local deterministic fixture/process tests, not a hosted GitHub/GitLab job. RAI-185 explicitly used the test JVM classpath and a dynamically built fixture JAR, not the assembled distribution. RAI-187's acceptance states that hosted CI claims are a non-goal. The First CI matrix is therefore good evidence for CLI semantics, not evidence that platform templates, real hosted artifact upload, fork isolation, or launcher/container PID1 forwarding work on every target.

3. **The artifact/exit design is substantially implemented, with acceptance deliberately narrower than the full contract.** [`HeadlessRunner.scala`](../../../modules/cli/src/main/scala/raider/cli/run/HeadlessRunner.scala) writes per-invocation artifacts; [`CiReport.scala`](../../../modules/cli/src/main/scala/raider/cli/run/CiReport.scala) provides check classification, JUnit escaping, path checks, and failure precedence. [The contract](../../ci-runtime.md) specifies six artifact files, safe GitHub/GitLab outputs, fork trust, package classpath/network constraints, and hosted-template verification. Existing evidence covers many local process clauses, but the card trail also records narrower edges: FCI-REPORT-02's separate post-run artifact-mutation fixture was deferred to RAI-210; package classpath isolation/no runtime dependency resolution and real platform-template jobs are not established by the First CI child fixture. RAI-210 adds a post-run artifact verifier, but is not a substitute for platform/release acceptance.

4. **There is local packaging and a clean-prefix smoke, not a published release.** RAI-193 records local-only JVM releases `0.1.1` and later `0.1.2`; the latter was installed into a clean prefix and launched a mock run with expected artifacts. The mock scout returned fixed text rather than inspecting the workspace. The launcher/Coursier and Java fallback smoke, checksums, malformed-install refusals, and a SIGTERM staging cleanup were exercised locally. The records explicitly leave Homebrew execution, Windows Scoop runtime behavior, hosted URLs, and publication unverified. RAI-204 also documents that `raider --help` was unsupported (exit 21) in its tested launcher path. No evidence supports a public download, functioning package-manager install, Windows support, or an end-user live coding workflow from the release.

5. **Reproducibility is improved and scoped.** RAI-240 measured nondeterminism in fresh dotc output, then demonstrated byte-identical repeated wrapper builds on the same tree/toolchain and reduced cross-clean-round variation to three `ids$package*` entries. RAI-252 removed that source of variance; RAI-253 then reports two clean build rounds with matching raw/canonical JAR hashes (`e629ab0b…`) on its macOS / Java 21 / Scala 3.9.0 toolchain, followed by six 20-scenario cross-ecosystem corpus runs with 160 findings and zero failures, plus a separate cancel-mid-response driver pass. This is strong same-host candidate evidence, not a cross-machine byte-reproducibility claim. RAI-253 explicitly scopes the pin to the measured host/toolchain. Its evidence is lane-local to the integrated candidate it built and does not replace gates on any later integrated tree.

6. **Cross-ecosystem execution is checked locally, not through external hosted consumers.** The independent corpus uses actual JVM consumer projects (including llm4s and langchain4j) with mocks and configured local OpenAI-compatible stands; RAI-253 reports all six consumer manifests green and separately tests the cancellation scenarios. This is substantive compatibility evidence. The records do not show hosted consumer CI, release consumption from a published artifact, or human/user validation. Keep those claims pending. `docs/tasks/m1.md` still marks follow-up RAI-254 ready to wire the cancellation scenarios into the corpus driver; the standalone driver evidence must not be described as integrated full-corpus coverage until that card lands.
