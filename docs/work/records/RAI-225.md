## Resulting behavior

All three observed red families in the process-api suites were
root-caused and eliminated. The two card families are fixed at their actual
root causes; a third family discovered during reproduction (same suites, same
acceptance criterion) is fixed with a two-line ordering change. No assertion
was weakened, no timeout extended, no sleep added; the only product change in
`submit` is a typed-semantics correction demanded by the frozen contract.

1. **Duplicate submit answered `input_rejected` instead of `duplicate_submit`
   (XE-PROC-03, product fix).** `Session.submit` dispatched on the phase only:
   `Phase.Settling → InputRejected("session is settling; submit refused")`.
   A fast mock run settles naturally right after `accepted`; a duplicate
   submit racing that transition hit the Settling branch and got the
   input-validation error for a session that ALREADY OWNS a root. The frozen
   contract (`contracts/process-api/README.md`: "submit while a root is
   owned: bounded `duplicate_submit` refusal") and fixture
   (`docs/fixtures/process-api/duplicate-submit.json`, XE-WIRE-02: submit
   after a root has been accepted → `duplicate_submit`) key the refusal on
   OWNERSHIP, not phase. Fix: `submit` answers `DuplicateSubmit` whenever
   `state.run.isDefined` (set atomically with `Phase.Running` in
   `startRoot`, never cleared); `input_rejected` stays reserved for its typed
   causes — pre-dispatch validation on a session that owns no root
   (`Phase.Active` validation miss, covered unchanged by the XE-WIRE-02
   secret-field test); the Settling-without-run fallback (EOF-clean /
   protocol-fatal / sigterm pre-dispatch) keeps the honest typed refusal.

2. **OutboundSpec coalescing gap raced its own saturation (test-side
   determinism fix, invariant unchanged).** The old harness forked up to 256
   `receipt` producers and exited on a `queueDepth >= 64` probe OR attempts
   exhaustion; both exits raced the forked fibers' asynchronous admissions.
   Worse, a writer forked BEFORE saturation takes one frame in flight and
   stays stuck on the gated sink, so the queue permanently holds at most
   MaxOrdinaryFrames − 1 while the writer is stuck — observation 65 always
   found room. Red shapes on base: `gapFrames = Vector()` (65/66/67 all
   admitted as ordinary frames) and, in the RAI-222 lane, `(66, 2)`.
   Fix: saturate SEQUENTIALLY to exactly `MaxOrdinaryFrames` BEFORE forking
   the writer (sequential receipts never suspend below the capacity bound —
   no forks, no probes, no scheduling dependence), then issue observations
   65/66/67 (all must coalesce), assert `openGap == Some((65, 3))` — a new,
   STRONGER assertion pinning the coalescing itself — and only then start
   the writer, release the sink, and verify the flushed gap frame
   `(65, 3)` end-to-end.

3. **Clean-EOF settled-note lost to the JVM exit race (product ordering
   fix, adjacent discovery).** `settleWithoutRun`/`settleWithRun` called
   `exitDone.succeed(exit)` BEFORE `noteSettled(exit)`; `exitDone.succeed`
   releases the main fiber to close the scope and `System.exit`, which
   under load won against the settling fiber's `System.err.println` — the
   diagnostic line was absent from stderr entirely (run4/run20 reds).
   Fix: emit the note BEFORE releasing the exit, so any normally-exiting
   child has necessarily written it. Test untouched.
