# RAI-259: Protected-path write policy and project-instruction injection for the native coder

Status: done. Date: 2026-11-02T00:54:37Z. Baseline commit/source: `953943f` (branch `lane/rai-259`, worktree `artifacts/lanes/rai-259`).

## Resulting behavior

**Write-path containment (deny-by-default).** New immutable `raider.tools.files.edit.WritePathPolicy(rootReal)` resolves every structured mutation target BEFORE any disk effect; `EditTool.resolveSafe` delegates to it, so all four mutating tools (`fs_edit`, `fs_patch`, `fs_patch_multi`, `fs_delete` — the last three through the existing `private[edit]` call sites) are covered at ONE enforcement point. A target is usable only if: (1) it is non-empty and workspace-relative (absolute targets refused — `root.resolve(absolute)` would discard the root); (2) the normalized candidate stays lexically inside the root (rejects `..` traversal); (3) the FULLY RESOLVED target — realpath of the nearest EXISTING ancestor joined with the non-existing remainder — stays inside the root realpath. Check 3 closes the pre-RAI-259 hole: a NOT-YET-EXISTING file under a directory symlink pointing outside the workspace was previously written THROUGH the symlink (the old code only realpath'd targets that already existed); it is now denied with `RA-TOOLDENY` ("symlink escapes workspace: …") and nothing written outside or inside. Denials stay model-correctable: the existing `toolOf` policy-denial mapping surfaces them as explicit `{"error":"RA-TOOLDENY","detail":…}` JSON tool feedback and the loop continues. The policy is an immutable value, so parallel delegated children (which share the parent's registry instance) observe identical decisions by construction.

**INTENDED CONTRACT CHANGE:** deny-by-default can now reject writes that the pre-RAI-259 code silently accepted — specifically creates through symlinked directories escaping the root, and absolute-path targets. Consumers relying on that behavior must re-point such targets inside the workspace.

**Project-instruction injection.** New `raider.tools.files.ProjectInstructions`: `DefaultFileNames = List("AGENTS.md")` (first match wins — precedence by order), `MaxBytes = 65536` (larger files load truncated and the section says so), fail-open (missing/blank/unreadable → `None`, base prompt unchanged — a broken instruction file never takes the coder down), deny-by-default containment for the instruction file itself (a symlink resolving outside the root is ignored; one resolving back inside loads). `ProjectInstructions.surface(basePrompt, rootReal, names)` returns the base prompt unchanged, or base + a clearly-marked "## Project instructions (from AGENTS.md at the project root)" section. `CoderPrompts.CoderSystemPrompt` became a `def` composing `surface` over the frozen base (renamed `CoderBasePrompt`, text byte-identical) at the process CWD — the default workspace root of BOTH frontends (ChatLoop and HeadlessRunner default `--workspace` to the CWD), so both call sites compile unchanged and both frontends now inject root-local instructions.

**Non-goals kept explicit.** `proc_run` remains out of file-policy scope (argv is fully visible; the file policy is not a sandbox — the REPL/plugin trust boundary is unchanged). No new policy DSL beyond the configured name list; `modules/runtime` main sources needed no change (children inherit the policy via the shared registry instance).

## Limitations / blockers

- **CWD-root rule for instructions.** `CoderSystemPrompt` reads the instruction file from the process CWD. Both frontends default the workspace to the CWD, so the default path is exact; an explicit `--workspace` pointing AWAY from the CWD still reads the CWD instruction file (the prompt is process-static, built where `AgentLoop` is constructed). Lifting this needs threading the resolved workspace root into prompt construction — separate card (touches ChatLoop/HeadlessRunner, outside this card's allowed paths).
- **`proc_run` is intentionally not covered by the file policy** (argv fully visible; a path policy on argv would be theater, and tool policy is not a sandbox). The child process can still write where the OS allows — unchanged trust boundary, documented in the policy scaladoc.
- **Process-local TOCTOU.** Containment is checked at tool invocation; combined with the RAI-260 mutation semaphore the check-then-write sequence is serialized in-process. An external actor re-pointing a symlink between check and write is outside the model (no sandbox claim).
- **Base prompt text staleness (pre-existing, untouched).** `CoderBasePrompt` still lists the six-tool surface (no `fs_patch_multi`/`fs_delete`) — frozen Phase 4.3 text; refreshing it is a separate prompt card, not this policy card.
- No REPL/PTY or provider-transport checks: this card changes no REPL, transport, or runner code; `fast`+`tools`+changed profiles are the semantically required gates.
