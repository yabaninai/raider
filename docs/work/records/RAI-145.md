## Resulting behavior

The unified multi-job lineage graph (one campaign + correlation-linked child
segments, ADR-032) now projects to an EXECUTABLE dry-run composition over the
ADR-031 runtime. For the BillingCi shape — baseline-check → repair(with
tools) → final-check → independent-reviews ×2 → boundary batch ×3 — the
projection emits: **phase defs per pipeline stage** (wire-native v2
`Phase` nodes), **delegation blocks where the contract links jobs** (real
parent-child edges from the joined stream; child-segment nodes nested inside
their `Delegation` def), and **batch fan-out as the recorded loop
composition**. Unlinked native roots stay separate (never joined by RAI-144,
so they cannot appear in the unified tree); malformed/unlinked segments
surface as typed entries, never silent merges.

- **New generator `UnifiedProjection`** (`raider.dsl.lineage.proj`): a
  deterministic, stateless source generator over the unified `LineageView`
  (same walk/emission discipline as the single-run `LineageRenderer`:
  pre-order, per-scope value binding with `n_*` variables, cross-scope input
  ids as string literals, named sub-`Program` vals spliced pre-order,
  `LineageStep.failed` for recorded non-success outcomes, renderer-parity
  escape disciplines — `\uXXXX` in literals for the pinned dotc 3.9.0). The
  `LineageStep` runtime module is UNTOUCHED (ADR-031 §2.2 stays exactly as
  accepted: only `Task.succeed`/`fail`/`map`/`flatMap`).
- **Frozen-verb pin (card choice).** The unified composition uses
  `raider.dsl.lineage.proj.runtime.LineageStep` + the frozen n-ary DSL verb
  `raider.dsl.composition.batch` for recorded sibling fan-out groups +
  `Task.map`/`flatMap` sequencing (the single observation boundary stays
  `Task.zio`; `batch` runs under the one effect interpreter — no second
  execution semantics). Justification: (a) the card mandates existing frozen
  verbs — `batch` is the n-ary ordered bounded fan-out the loop can actually
  dispatch (COMP-01: results keep INPUT order, so the report vector stays the
  graph's pre-order regardless of fiber completion order); `batch.all` is
  arity-2 only and would need nesting gymnastics for the boundary trio;
  `Program.andThen` composes two Programs and adds nothing over the
  `Task`-level chain for a `Vector[StepReport]` output. The illustrative
  `pipeline`/`parallel`/`batch` SYNTAX is not an approved API and never
  appears (fixture-asserted). Emitted form:
  `batch(List(<sub-programs>), <recorded parallelism>)(p => p(()))` inside the
  parent scope's chain, flattened via `Task.map` into the pre-order vector.
- **Fan-out honesty (no invented parallelism).** A fan-out group is a
  RECORDED composition fact (`FanOutGroup(parentId, members, parallelism)`)
  carried into the projection and VALIDATED against the graph: members must
  exist, be `Delegation` nodes, share the parent, and form one contiguous
  in-order sibling run; violations are typed `BadFanOut`, never "fixed".
  Parallelism is never inferred from node order or timestamps. Edges come
  only from the reduced graph (provenance/correlation).
- **Provenance + typed segment report carried.** `GeneratedProjection`
  exposes `provenance` (verbatim ADR-032 artifact pointers) and `segments`
  (typed `SegmentEntry`: `Linked` / `Incomplete(detail)` / `Unlinked(detail)`)
  and emits both as DATA vals in the generated artifact (`runProvenance`,
  `segments`). Payloads stay in lineage-data, addressable by dataRef keys.

### Fixture shape (RAI-142 execution discipline: render → pinned dotc → load → `Task.zio`)

`UnifiedProjectionExecutionSpec` (cli test) builds the BillingCi-shape unified
stream with the REAL multi-job machinery (MJE join-level approach: `EventHub`
+ `JobManager` with the composed capture+ledger listener, real child jobs
per stage, `EventsJsonlWriter`, `MultiJobExport`; introductions published the
DelegationEvents way under the child's own id; connect order pinned by
bounded segment-count polls; per-stage settle waits keep each child's tail
ahead of the next stage's fork record). The campaign's five **stage phases
are a documented fixture stand-in**: the product has no live phase-emission
path yet (ADR-024 hub seam frozen, `LoopEvents` has no phase surface), so the
fixture inserts `phase_started`/`phase_finished` v2 envelopes at
deterministic positions around the REAL machinery envelopes (before each
stage's canonical fork record, after the stage's last joined child line) and
re-derives the export-canonical per-job seq space (dense 1,2,3… in file order
— the exporter's own rule). The enriched stream is written to a file and read
back through the versioned reader, so the reduction input is the FILE;
delegation joins, correlation keys, fork records and the provenance record
remain real machinery output.

## Projected unified composition excerpt (real artifact, `rai145-uni01.scala`)

```scala
// Generated by Raider lineage projection (ADR-027/ADR-032 unified multi-job). Do not edit — comparator detects edits.
// ADR-031 dry-run description: ... Not a replay or rerun entrypoint.
// Unified multi-job projection (RAI-145): phase defs per pipeline stage, delegation
// blocks per correlation-linked child segment (ADR-032), recorded sibling fan-out groups
// composed with the frozen DSL verb batch (raider.dsl.composition.batch; results keep
// input order). No parallelism is invented: edges come only from the reduced graph.

import raider.core.Program
import raider.dsl.composition.batch
import raider.dsl.lineage.proj.runtime.{LineageStep, StepReport}

object lineage_j_1:
  val runProvenance: Vector[(String, String)] =
    Vector(("work_dir", ".../jobs/j_2"), ("events", ".../jobs/j_2/events.jsonl"), /* … 16 pointers */)
  val segments: Vector[(String, String, String)] =
    Vector(("j_2", "inv-1", "linked"), /* … 8 linked */)

  val phase_reviews: Program[Unit, Vector[StepReport]] =
    Program.fromFunction("phase_reviews") { _ =>
      LineageStep.phase("j_1:n11", "reviews", None, Vector.empty, nesting = 1)
        .flatMap { n_j_1_n11 =>
          batch(List(delegation_ci_review, delegation_ci_review_2), 2)(p => p(()))
            .map { n_j_1_n12_batch =>
              n_j_1_n11 ++ n_j_1_n12_batch.flatten
            }
        }
    }

  val delegation_ci_review: Program[Unit, Vector[StepReport]] =
    Program.fromFunction("delegation_ci_review") { _ =>
      LineageStep.delegation("j_1:n12", "ci-review", None, Vector("j_1:n11"), nesting = 2)
        .flatMap { n_j_1_n12 =>
          LineageStep.model("j_5:n2", "review-model", 1, Some("j_5/round-1"), Vector(n_j_1_n12.head.id), nesting = 2) // data: j_5/round-1
            .map { n_j_5_n2 => n_j_1_n12 ++ n_j_5_n2 }
        }
    }
  // … phase_baseline_check / phase_repair (with the bash tool call) / phase_final_check /
  //    phase_boundary (batch of 3) / program = the five phase defs chained pre-order
```

## Carried packet risks (addressed or scoped)

1. **Fork records are ROOT-anchored in the export** — addressed by not
   assuming any anchoring: the projection consumes only the reduced unified
   tree (`SessionGraphView` over `reduceWire`); delegation nesting follows the
   recorded parent edges wherever they point. Per-level anchoring (nested
   delegation chains) remains a PRECONDITION for nested-delegation shapes and
   is out of scope here — the generator walks whatever tree the contract
   produces, but no fixture covers nesting deeper than phase → delegation →
   child (RAI-146 corpus territory).
2. **`raider replay` reads v1 only** — honored: the unified export is never
   replayed from disk through the replay layer; the fixture executes
   in-process (reduce over the versioned reader's envelopes + generated
   artifact), exactly like MJE-01.
3. **Unlinked-segment adversarial case had no named fixture** — this card's
   UNI-02 is the first named coverage: the stray job (captured, never
   introduced) is asserted absent from stream, tree, and provenance, with the
   typed `Unlinked` entry. RAI-146 VR-02 still owns the versioned corpus.

## Limitations / blockers

- **Phase emission stand-in (fixture-level).** The product runtime cannot yet
  emit v2 phase envelopes (ADR-024 seam frozen; `LoopEvents` has no phase
  surface) — the fixture inserts the campaign's stage phases at deterministic
  positions and re-derives the export-canonical seq space (documented in the
  spec scaladoc). Everything else in the stream is real machinery output. A
  future wiring card flips real phase emission on with zero generator changes
  (the generator consumes the reduced graph, emission-agnostic).
- **Every stage is a delegated job in the fixture.** The BillingCi
  application pattern (each stage its own native job) keeps all campaign-side
  activity phase-markers + fork records; inline campaign model rounds would
  re-parent subsequent delegations to the last-seen round (documented reducer
  fallback), so the fixture pins the phase-per-stage shape instead. This is a
  fixture-scope decision, not a product constraint.
- **Fan-out groups are a projection INPUT** (recorded loop composition,
  validated against the graph) — the unified graph itself cannot distinguish
  a batch fan-out from sequential sibling forks. Deriving fan-out from
  emission-overlap evidence would need the pre-canonicalization stream and a
  timing heuristic; the heuristic path is exactly the "invented parallelism"
  the card forbids, so it was not taken.
- The zero-dispatch probe covers the dsl/cli pipeline (render, compile, load,
  execute); the dotc subprocess is a separate JVM by construction.
- Evidence binds to the manifests' per-file source snapshot (mode
  `git-status`, run IDs `20261013-144009-1096-0001` and
  `20261013-144401-2011-0001`); this record is operational text written after
  the gate runs.
