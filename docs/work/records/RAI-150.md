## Resulting behavior

`SessionGraphView.toView` now POPULATES `NodeView.inputs` from the graph's
dataflow edges (`SessionNode.inputs.map(_.value)`, ADR-031 §2.6): 1:1, in the
graph's own edge order — no sorting, no dedup, no invented ids. Nodes without
edges (phases by definition; models/tools/delegations with no upstream) render
the empty vector honestly. The adapter stays pure (no IO), deterministic
(same graph → structurally equal view on repeat), and confined to the cli
layer; the dsl types, renderer, wire schema and graph model are untouched.
Because the renderer does not consume `inputs` yet (RAI-141 future work), all
golden renders stay byte-identical — pinned by the existing VIEW-A-02 tests,
now extended to also pin the populated input vectors against the frozen
golden documents.

`SessionGraphViewSpec` pins: model → tool edge (n2 ← n1), cross-node tool →
tool edge into the FAILED tool (n3 ← n2), multi-input edge order (n5 ←
(n1, n3)), honest empties (phase n0, first model n1, delegation n4, all
tiny-graph nodes), golden deep-tree cross-subtree edge (n3 ← n1), inputs
reference only existing node ids, triple-conversion determinism, and the
input graph is not mutated.

## Limitations / blockers

1. **BLOCKED (contract change required): `NodeView.outcome`.** The card says
   "populate NodeView.outcome from the recorded ToolCall outcome class" and
   SGB-02 expects "outcome None" degradation, but the frozen dsl projection
   type `NodeView`
   (`modules/dsl/src/main/scala/raider/dsl/lineage/proj/LineageProjection.scala:15-28`)
   declares only `id/kind/parentId/children/dataRef/inputs` — there is NO
   `outcome` field to populate. Reproducer: any attempt to carry
   `SessionNode.ToolCall.outcome` (a `ToolOutcome` = Succeeded/Failed/
   Cancelled/Timeout) in the view has no target; the only in-schema slots are
   contract-frozen (`NodeKind.ToolCall.recovery` must stay exactly
   ReadOnly/Idempotent/Mutating per lineage-data v1; `dataRef` is the
   lineage-data join key), and `modules/dsl/**` is outside this card's allowed
   paths ("extending the path boundary requires a separate scope card").
   Required follow-up: a dsl schema card adding e.g.
   `outcome: Option[String] = None` to `NodeView` (mirroring the ADR-031 §2.6
   `inputs` addition), an ADR amendment documenting the mapping
   (ToolOutcome case name → string; `Failed` reason stays in lineage-data),
   and renderer failed-marker consumption (RAI-141). The adapter invents
   nothing in the meantime; the failed tool is still covered model-side by the
   unit fixture (`ToolOutcome.Failed("exit 1")` on n3).
2. **Packet/repo discrepancy (documented, not worked around):** the card
   context claims "the compile-gate test adapter already pins the populated
   contract", but at baseline `67bca1e` the compile-gate adapter
   (`GraphToView` in `LineageCompileGateSpec.scala:324-389`) constructs 5-arg
   `NodeView`s (empty inputs) and is outside this card's allowed paths, so it
   was left untouched. The compile gate stays green because the renderer
   ignores `inputs`; "compile gate green on the populated view" is therefore
   evidenced via the integrated suite runs, not by the gate adapter exercising
   `SessionGraphView` (it uses its own test-local copy by design, per its
   snapshot-discrepancy note).
3. "Rendered projection threads real dependency values" (SGB-01) is RAI-141's
   renderer integration; this card delivers the populated view the renderer
   will consume. No renderer change was made (non-goal).
4. Two intermediate gate runs FAILED on scalafmt-check before the fixes above;
   recorded honestly. Final evidence is from the three consecutive passed runs
   and the profile run, all on the checked source fingerprints above.
5. Real paid calls: none; everything ran on local/mock fixtures.
