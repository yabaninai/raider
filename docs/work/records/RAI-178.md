The full module suite went from red-by-hang (60+ min wedge, WIR-01 internal 5-minute timeout, E01/E02/E03/EW/PHE internal timeouts, ~20 suites never producing output) to green ×5 consecutive at the final source fingerprint: 450 passed / 0 failed / 0 ignored per run, 136–145 s per run. Root cause (fiber-verified, not inferred): product-internal settle/export polls (`EventExport.awaitCaughtUp` at `EventExport.scala:119`, `MultiJobExport.pollUntil` at `MultiJobExport.scala:638`, plus the readiness polls converted in the RAI-157 sweep) sleep via `ZIO.sleep` on the **ambient clock**. Specs that drive this machinery as plain `ZIOSpecDefault` run it on the frozen zio-test **TestClock**: the first poll iteration whose condition is not yet satisfied suspends on a sleep that never fires, and the wall-clock deadline escape in those loops is only re-checked after the (never-returning) sleep. The run then sits idle (7 % CPU measured) until its `TestAspect.timeout` fires — or forever in suites without a timeout aspect, which also wedged the forked JVM's test-class runner slots and left ~20 innocent suites queued with no output.

The correction is fixture-only and assertion-neutral: `@@ TestAspect.withLiveClock` (the established house pattern already used by `ResumeCommandSpec`, `CiAdapterBatchSpec`, `EventExportSpec`) was added to the specs that drive the live export/headless machinery but still ran on the frozen TestClock. No assertion, expectation, deadline, budget, threshold, skip, or gate-policy value was changed anywhere. A real `raider run`/chat/export process never runs on a frozen clock, so the live clock is the production-faithful fixture for these specs.

## WIR-01 diagnosis (WIR01-STAB-01)

WIR-01 is the test in `raider.cli.run.CoderDelegationRunSpec` (RAI-154), bounded by `@@ TestAspect.timeout(300 s)` — the "internal five-minute deadline". It does NOT live in `WorkflowLaunchSpec` (the card/assignment prose conflated the two; `WorkflowLaunchSpec` hosts CWF-D01/D03/WRI-02/WRI-03 and had the same disease).

Reproduction at baseline (standalone, no suite load): `sbt --batch 'raiderCli/testOnly raider.cli.run.CoderDelegationRunSpec'` fails deterministically — "Timeout of 5 m exceeded", 302 s total, 20.8 s user CPU (≈7 % CPU): an idle hang, not CPU starvation. Timeline (log `02-wir01-standalone-1.log`, hash `9ed89de…`): the stand answers all three model rounds in < 40 ms (`delegate` → `await_agent` → final text), then nothing.

Fiber trace (WIR01-STAB-01 deliverable): a temporary live-clock watchdog in the spec forked the body and captured `zio.Fiber.dumpAll` every 15–30 s. Seven dumps, all identical (stable deadlock): fiber-11 `Suspended` in `raider.cli.run.EventExport.awaitCaughtUp.loop (EventExport.scala:119)` — the `ZIO.sleep(2 ms)` poll on the frozen TestClock; fiber-21 (`HeadlessRunner.executeAsJob:365`) waiting on the collector; three child-capture consumers and both hub forwarders idle on empty queues; everything upstream already finished. Log `03-wir01-fiberdump.log`, SHA-256 `14cb24da3f72ed5cc9b3681df487653beddd3cdc4824eda4008e024f5a32a137`. The diagnostic edit was reverted; the committed spec contains only the `withLiveClock` aspect + comment.

Blocking-wait adjudication: for the implicated fixtures there is **no residual blocking (Java-sleep) wait** — the RAI-157 sweep removed those. The stalls are the opposite: non-blocking `ZIO.sleep` polls that require clock progress the TestClock never provides. `EventExport.awaitCaughtUp`'s wall-deadline escape (`System.currentTimeMillis`) is unreachable because the loop re-checks it only after the suspended sleep returns. The mechanism is identical for the export-family suites (PHE-01/LIN3-01 at `PhaseEmissionExportSpec`, EW-01/EW-03, E01, E02, E03) and for `TaskCaptureSpec`, where `fiber.interrupt` wedges forever in runJob's uninterruptible `ensuring(awaitCaughtUp)` (no timeout aspect — this is what occupied runner slots and silenced ~20 downstream suites).

Why it regressed when it did: the sweep (03fba34, in the RAI-157 lane) made WIR-01 deterministically red from its merge (both RAI-157 closure module attempts failed only WIR-01); the 2026-10-18 merge-all brought LIN-03/RAI-173 live-projection maintenance into the same export paths, extending the freeze to PHE/LIN3-01/EW/E01/E02/E03 at `64edb8a` (matches the board's integrated-gate failure list). Under heavy machine load the freeze also hits specs whose poll conditions normally early-exit (observed: `MultiJobExportSpec` family, `HeadlessRunnerSpec` RUN-01..03 in run `07-full-module-postfix2-1.log`), because load delays the hub forwarder hops between the first check and satisfaction.

Post-fix standalone: WIR-01 green in 517 ms (then 2 s warm), 3/3 runs; `TaskCaptureSpec` from infinite wedge to 318 ms; E01 10 min-timeout → 14 s; E02 2×10 min → 18 s; E03 5+10 min → 28 s; PHE 2×2 min → ~7 s (see `04-*`, `06-*`, `09-*` logs).

## Limitations / blockers

- The zio-test TestClock freeze is a **fixture/product interaction**, not a product bug for live processes (a real CLI process runs on the live clock). A deeper product-side hardening (TestClock-safe polls or a documented clock contract for embedders) would be a main-source change outside this card's allowed paths.
- Per-suite wall times inside the single forked JVM are interleaved; the timestamped streams are the authoritative timing evidence, and the table above gives representative windows.
- The ×5 matrices and gates ran at load ~5–12 (other lanes active). Extreme oversubscription (load ~37, observed in the first baseline run) can still slow real-process fixtures (dotc children, SIGTERM tests), but no frozen-clock hang remains; the whole-build gate margin is ~2.4× at representative load.
- `withLiveClock` makes those 21 suites wall-clock-dependent (previously they hung instead); their internal budgets (unchanged) bound them.
- Lane evidence applies to this snapshot; integrated-candidate acceptance (merge + rerun) remains with the coordinator.
