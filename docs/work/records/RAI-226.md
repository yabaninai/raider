## Resulting behavior

The test fixture harnesses `driveCampaign` and `driveNested` in `MultiJobExportSpec` now fork the delegator body only **after** `join.campaign(handle.id)` commits, matching the documented runner discipline (`MultiJobExport.scala:163-166`: "children are forked by the campaign's own loop", i.e. after campaign registration).

This removes the load-sensitive race that produced the MJE-03c red: if a child introduction was delivered before `join.campaign` ran, `MultiJobExport.connect` read `campaignRef = None` (line 302), computed `joinedToRun = true` (line 332; the fixture registers no fork owner), registered the child segment (line 335), then hit the loud guard at lines 340-349 — `ZIO.die("MultiJobExport: campaign job id not set before a fork connected")` — killing the daemon capture fiber after registration but before the fork record and copies appends (lines 369-370). The observed MJE-03c failure shape follows: run provenance pointing at `jobs/j_1`, no fork record or copies on the run stream, a 0-byte child segment file on disk, `strict = Right(...)` instead of `Left(MissingTerminal(childId))`, `childId = "<none>"`.

The root cause was test-side; the product's loud `connect` guard behaved as designed and is unchanged. The die remains reachable for genuine contract violations (detection intact, proven by the sabotage probe below). Uniqueness of the mechanism: `rootDone` is read at line 301, before the registration at 335, and `rootDone=true` at that point is impossible (it requires the Terminal export, which requires the pin, which requires registration), so the guard die is the only path matching all observed artifacts.

No public API or schema change. No sleeps added; the existing bounded deterministic waits (`pollUntil` pins) are unchanged.
