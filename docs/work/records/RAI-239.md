## Resulting behavior

`scripts/bootstrap.sh` provisions the pinned 31-jar consumer closure (gitignored `artifacts/tools/m2`) so a fresh checkout becomes buildable without sbt/Coursier. The pre-existing RAI-218 toolchain bootstrap is preserved verbatim behind a command dispatch:

- `bootstrap.sh` / `bootstrap.sh all` — toolchain bootstrap, then m2 provisioning (backwards-compatible default).
- `bootstrap.sh toolchain` — RAI-218 toolchain behavior unchanged.
- `bootstrap.sh m2 [--source DIR | --download] [--manifest FILE] [--target DIR]` — provisions the 31 artifacts pinned in `contracts/acceptance/cross-ecosystem/consumer-deps.json`. Default mode downloads from Maven Central (`https://repo1.maven.org/maven2`, snapshot/classifier coordinates rejected); `--source DIR` copies offline from an existing m2-layout store. Every artifact is verified (sha256 + size) against the manifest before installation, installed atomically (fsync, `chmod 0644`, tmp+rename), and the whole closure is re-verified from disk before exit. Cross-process safety via flock on `artifacts/tools/.m2-bootstrap.lock`; existing correct jars are reused (`already verified`); a corrupt target jar is repaired from a verified source; unrelated files in the store are never deleted. Exit codes: 0 success, 1 artifact corrupted/missing (named with expected/got sha256 and source path), 2 usage/manifest error, 64 unknown command.

`scripts/README.md` (new) documents both bootstrap layers, usage, verification guarantees, and exit codes. Note: `scripts/build/compile.sh` error output already pointed contributors at `scripts/bootstrap.sh`; it now leads to a working fix for missing consumer jars too, not only the toolchain.

## Limitations / blockers

- Scratch s1 needed the 31 non-pinned toolchain jars copied manually to run the AFTER compile probes; provisioning the toolchain layer is the existing RAI-218 `toolchain` command, which was regression-verified but not exercised as a fresh-download in this card's probes.
- Download mode trusts Maven Central availability and the pinned sha256/size values in `consumer-deps.json`; no mirror/proxy support.
- The card contract's consumer-closure verification (`31/31 artifacts verified OK`) was re-confirmed against the worktree store before authoring; all 31 Central URLs returned HTTP 200 with matching Content-Length during pre-flight.
- All evidence was produced under heavy sibling-lane load (load average 96–311 during the runs). Two initial `sbt-compile` gate failures were traced to stale/poisoned zinc state (deterministic E008 contradicting both source and classfile; clean rebuild of `modules/*/target` + `project/target` fixed it with zero source changes). Cross-lane zinc isolation is a registered wave-F infra card; until it lands, a clean target rebuild is the recovery step for this failure signature.
