## Resulting behavior

Unified lineage now has a FROZEN, versioned multi-root acceptance corpus plus
an independent verifier spec — the protected acceptance surface of the unified
lineage feature (future corpus/pin changes go through the RAI-146 review
lineage, per the card).

- **Corpus** (`contracts/lineage/unified/`, `corpus version 1`): four golden
  unified streams + four negative-control streams (JSONL, authored through the
  REAL codecs; per-job seq dense in file order; children as v2 envelopes with
  `invocationId`, campaign frozen payloads at v1, phase/provenance payloads
  v2 — ADR-032 shapes). Each case ships a frozen `.expected.json`
  (graph-hash pin, exact executed report tree, provenance record, typed
  segment entries, recorded fan-out groups, generated-source substring pins +
  whole-artifact sha256 pin). `manifest.json` pins the sha256 of all 19
  corpus files; `README.md` documents construction rules, derivation rules
  (expectations are independent contract-semantics derivations from the
  streams — ADR-031 §2.3 pre-order/nesting, ADR-032 §3 hash policy — never
  snapshots of generator internals) and the change policy.
- **Verifier** (`raider.cli.lineage.UnifiedCorpusVerifierSpec`): reads the
  corpus from disk, re-hashes every manifest file, then drives the product
  pipeline — versioned reader → strict/partial reducer → graph view →
  unified projection → pinned dotc 3.9.0 compile → `Task.zio` execution —
  and asserts the frozen pins. Every compile runs in its own unique temp
  directory (VR-03 isolation); parallel verification produces the pinned
  results.
- **Generator fixes** (packet-authorized small typed fixes, each with a
  corpus reproducer; `UnifiedProjection.scala` only, +31/−19 lines):
  - **(f1)** a scope whose ONLY emission element is a fan-out group emitted a
    bare `batch(...)` expression — `Task[List[Vector[StepReport]]]` where the
    `Program` body needs `Task[Vector[StepReport]]`: a type error under the
    pinned dotc. Fix: the single-element fan scope emits
    `batch(...)(p => p(())).map(_.flatten.toVector)`. Reproducer: corpus
    `case-4-pure-fanout-roots` (root scope is exactly one fan-out group) —
    compiles and executes the exact 4-report tree; before the fix the
    generated source did not compile.
  - **(f2)** a validated fan-out group whose parent is NOT a def node (e.g.
    delegation forks hanging under a model round — the reducer's recorded
    parenting) was carried in `GeneratedProjection.fanOut` but emitted
    SEQUENTIALLY, because scope matching required `group.parentId ==
    scopeNode`. Fix: scope matching by member-call presence — a validated
    group is claimed by the ONE scope whose steps hold its member calls (def
    body for phase/delegation parents, enclosing scope otherwise, root scope
    for root-level groups). Every validated group is now composed exactly
    once as recorded `batch`; `fanOut` never claims a group the source does
    not compose. Reproducer: corpus `case-2-delegation-tree` (fan-out
    parented to the orchestrator model round) — the verifier asserts the
    `batch(List(delegation_worker, delegation_worker_2), 2)(p => p(()))` line
    and the exact 7-report tree.
  - Both fixes leave the existing RAI-145 evidence green unchanged
    (`UnifiedProjectionExecutionSpec` 3/3, exact UNI-01 source pins intact —
    its groups all have phase parents, matched in the same scopes as before).

## Limitations / blockers

- **Pre-existing full-suite flake (external, unrelated to this card).** Two
  `make quality-changed QUALITY_EXECUTE=1` runs on the final fingerprint were
  red from intermittent failures in suites this card does not touch
  (`ReplayProductCliSpec` LIN13-01 process spawn; ui `SessionRegistrySpec`
  TAB focus invariant). Both pass in isolation and the cli module (which
  contains every surface of this card) was green in every run, including the
  final all-green run. Both red manifests are retained as evidence; neither
  failure was masked or attributed to this card. A flake-hunting card for
  those two suites is worth scheduling (owner decision).
- **Corpus provenance is authored, not machinery-recorded.** The streams are
  hand-authored through the REAL codecs and mirror the RAI-145 machinery
  conventions (join order, canonical fork records, provenance layout), but
  they are not captures of a live MultiJobExport run — machinery realism was
  RAI-145's (UNI-01) evidence; this card freezes the ACCEPTANCE surface. The
  README documents every construction rule so a reviewer can recompute any
  pin by hand.
- **Expectations derived from contract semantics, reviewed once.** The
  expected trees were derived from the reduced views (pre-order + ADR-031
  §2.3 nesting), independently of generator internals; one transcription
  error (case-2 worker-b delegation input) was caught by the first verifier
  run — the product was RIGHT, the frozen expectation was corrected and
  re-manifested (`2c5306f3…`). This is the intended direction: the corpus
  constrains the implementation, not vice versa.
- **Object-name note for reviewers:** the generated object name derives from
  `view.runId` = `SessionGraph.rootId.value` (`lineage_root_unified_corpus`
  for every corpus graph — all cases share the frozen rootId). RAI-145's
  fixture fed the campaign job id as the projection input runId; the view
  contract's runId is the graph root id. No pin depends on the choice beyond
  the frozen source shas.
- Evidence binds to the manifests' per-file source snapshot (mode
  `git-status`, run IDs in the commands table); this record is operational
  text written after the gate runs.
