# RAI-165: work record

Status: partial. Date: 2026-10-18. Baseline commit: `0f73be7a2b429b40bb7636b94b0313cce34594f1`; branch: `lane/rai-165`.

## Resulting behavior

Added an approval artifact subsystem under the runtime SDLC package. A headless checkpoint writes an atomic schema-version-2 `approval-request` carrier containing the checkpoint ID, canonical RAI-164 `CandidateIdentity.digest`, and expiry, and returns a `NeedsApproval` result with exit code 25. It neither reads stdin nor holds execution state. A separate JSON decision is strictly decoded and bound to request checkpoint/digest/expiry. A fresh `recheck` calls a current-state reader and verifies the candidate digest, policy/state consistency, task/base, candidate-bound current evidence, expiry, denial, and owner capability before returning authorization. No continuation/fiber is stored or resumed.

The decision and request files are evidence, not capabilities; the current invocation must still provide the capability. Request carrier JSON is additive and leaves schema-v1 untouched.

## Limitations / blockers

- The full CLI no-TTY invocation and actual `run.json`/events artifact path do not yet dispatch SDLC checkpoints; adding an API in the existing runner without an established workflow/checkpoint input boundary would invent integration semantics. The reusable headless checkpoint correctly writes a request and exposes exit 25, but end-to-end CLI artifact/exit acceptance remains pending.
- Request/decision authenticity and signature/key management are intentionally unspecified; ADR-030 leaves them as implementation details. Files do not grant authority.
- No real external integration, paid calls, or live services were used.
- One supplementary profile attempt failed because two sbt gates were launched concurrently from the same checkout. The serial retry passed and is the recorded profile evidence.
