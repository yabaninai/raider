## Resulting behavior

**(1) Headless coder-agent delegation wiring (WIR-01).** `raider run --agent
coder` can now delegate. New `CoderDelegationWiring` (`raider.cli.run`) builds
the EXISTING runtime-contracts §11 surface — `DelegationToolset.make` +
`DelegationEvents(hub, root)` — over the run's own `JobManager` and `EventHub`,
and augments the coder's coding registry with the four §11 model tools
(`delegate` / `await_agent` / `cancel_agent` / `list_agents`). The policy is
the toolset's own, unchanged and typed: the agent whitelist
(`CoderDelegationWiring.AllowedAgents` = `CliArgs.BuiltInAgents`; children
structurally cannot re-delegate — a forked child runs the base registry only),
`maxChildren` budget feedback, and the construction validations
(`maxConcurrentTools >= 2`, no base-registry name clashes, positive mailbox
capacity) as `RaiderError.Configuration` refusals. No new policy layer was
invented. `HeadlessRunner` changes are minimal and localized: `manager`/`hub`
are threaded into `execute` (two parameters + call-site args) and the coder
branch augments its registry after the backend is built; other agents keep the
empty registry and are behaviorally unchanged. Forks join the run's multi-job
export through the already-shipped capture (composed listener), so the
end-to-end path needs zero exporter changes — the fixture proves MJE-01
semantics through the product entry: a REAL child job joins the run's single
`events.jsonl` (correlated v2 envelopes), exactly ONE canonical fork record in
the campaign stream, exactly ONE `run_provenance` record immediately before
the campaign Terminal, strict `reduceWire` Right with the Delegation node
anchored in the campaign stream, lineage-data SCHEMAVERSION 2 with the
provenance record, `lineage.scala` beside the checkpoint. The fixture drives
`HeadlessRunner.run(args, env)` against a LOCAL OpenAI-compatible stand (JDK
HttpServer, loopback, ephemeral port, content-routed turns) — no real network,
no paid calls, the credential travels only through the injected test env.

**(2) Per-level fork anchoring (WIR-02), typed reproducer first.** The frozen
`Delegated(childJobId, agent)` payload carries no parent id, so the topology
source is the WIRING: `MultiJobExport.anchorForkUnder(child, forkingJob)` is a
Scala-level registration (a declaration of an existing fact, same trust level
that publishes the fork record), consulted by `connect()` at join time.
Resolution: a registered forking job anchors the canonical fork record in ITS
per-job stream (`nextSeq` of that stream); an UNREGISTERED child anchors in
the campaign stream exactly as before — the single-level export is
byte-identical (MJE-01/02/03 pins unchanged, ×4 runs). Post-terminal honesty
now applies PER LEVEL: a fork observed after the anchoring job's Terminal was
exported connects as a NATIVE-ONLY segment (nothing joins; no
`ReduceError.AfterTerminal` invented edge). A registration naming a job that
has not connected is a loud defect (the same "never a silent wrong-shape
export" convention as the campaign-not-set guard); the wiring discipline (the
forking job's own introduction connects before it forks) is pinned by the
fixture. The reproducer (commit `b87804e`, test RED, exit 1): a
root→child→grandchild fixture where BOTH fork records landed in the campaign
stream — the grandchild's `Delegated` record was `campaignRecs = [child,
grand]`, `childStreamRecs = []`, and the grandchild Delegation node parented
inside the campaign (`j_1:n4` under `j_1:n3`) — the wrong root→grandchild edge
of RAI-144 review risk 1. After the fix (commit `e91dd0c`): the grandchild's
record anchors in the child's stream; the grandchild Delegation node's parent
resolves into the CHILD's stream (the reducer's shipped parent rule — current
model round of the carrying stream, else phase, else base edge — unchanged);
strict reduction Right; per-job export seqs stay dense; GraphHash 64-hex. The
reducer itself was NOT touched.

**(3) Unified lineage-data writer (WIR-03).** `RunLineageArtifacts.write` no
longer refuses phase-bearing graphs. Wire-native `SessionNode.Phase` nodes (v2
`phase_started`, ADR-032) are written as real `phase` nodes with a
`<job>/phase-<seq>` dataRef (the reducer's node-id convention; seq is unique
per job, so the ref is collision-free) binding `PhaseData(name, note)` — the
graph's own verbatim phase data. Nothing is invented: the wave-1 graph node
carries no recovery and no timestamp, so `recovery` stays ABSENT (optional
non-null v2 field, omitted on the wire) and `atMs` records the schema's
not-captured 0. The v1/v2 decision has ONE source, `RunLineageArtifacts.schemaVersionOf(graph,
provenance)` (public): schemaVersion 2 exactly when the run exported the
provenance record OR the graph carries phase nodes; 1 otherwise. The
summary.md artifacts line reports that same rule (one-line `HeadlessRunner`
change). Delegation-free, phase-free runs are byte-identical to the frozen v1
document (the v1 path is untouched; pinned by fixture: `raw == doc.toJson`,
`startsWith("{\"schemaVersion\":1")`, no `provenance`/`phase`/`invocationId`
keys). Refusals stay typed: view/render/store/io failures remain the
`ArtifactError` family (fixture: a structurally inconsistent graph → typed
`ArtifactError.View`, no files invented). Delegation nodes keep the wave-1
convention (no dataRef entry) — see Limitations.

## Limitations / blockers

- Nested delegation is still not PRODUCIBLE by the runtime toolset itself
  (`DelegationToolset` children run the base registry — `modules/runtime/**`
  is outside this card's allowed paths). Per-level anchoring is exporter-side
  and driven by the wiring registration; the runtime card that eventually
  enables child re-delegation must register `anchorForkUnder` at the child-loop
  construction site (the discipline the scaladoc pins) and respect the
  connect-before-fork ordering. The fixture pins the semantics so that card
  needs zero exporter changes.
- Delegation nodes keep the wave-1 lineage-data convention (no `dataRef`, no
  `delegationData.invocationId` entries) — the per-segment correlation lives on
  the joined v2 envelopes of `events.jsonl` plus the top-level provenance
  record, exactly as RAI-144 shipped; run-written `delegationData.invocationId`
  entries remain deferred to the corpus/dataRef-convention owner (RAI-146
  territory), unchanged by this card.
- Phase nodes record `atMs: 0` (the wave-1 `SessionNode.Phase` carries no
  timestamp; the schema requires the field — 0 is the not-captured marker) and
  never carry `phaseData.recovery` (the graph does not hold it; inventing it is
  forbidden). When a live phase emitter ships recovery on the wire, the graph
  model — not this writer — must carry it first.
- Pre-existing flake OBSERVED once: `MJE-03b` failed under 3-suite parallel
  load (`full = Left(MissingTerminal(j_2))` — the child's Terminal missed the
  fold inside the fixture's 2 s `drain()` budget). The unregistered anchoring
  path this card touches is semantically identical to the pre-change code
  (registrations absent → campaign anchor, unchanged gates), and the test was
  green in every dedicated rerun (×5) and in BOTH full gate `sbt test` runs.
  Recorded honestly as a pre-existing RAI-144 fixture timing risk, not fixed
  here (another card's acceptance fixture; the full-suite gate runs are green).
- No live providers, no paid calls: the only network in evidence is the
  loopback JDK HttpServer stand inside the test JVM; the stand key is a fixed
  test constant in the injected env map (never argv, never a real secret).
- Evidence binds to the two manifests' per-file source snapshots (run IDs
  `20261013-234239-71424-0001`, `20261013-235117-89661-0001`); the manifests
  and fixture logs live in the lane worktree (`artifacts/` is gitignored, the
  scratch logs under `…/opencode/rai154/`); this record is operational text
  written after the gate runs.
