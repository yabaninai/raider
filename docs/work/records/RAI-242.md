## Resulting behavior

The llm4s consumer corpus is extended with two mid-provider-response cancellation scenarios (llm4s consumer only; langchain4j untouched per non-goals):

- `cancel-mid-response`: the consumer submits a coder task, waits for `dispatch-accepted`, then proves mid-response placement client-side: the scripted round-1 provider response (SSE/plain tool_calls -> `proc_run` touch) has been fully consumed and executed — the workspace marker `marker.txt` exists (bounded 50 ms poll, 20 s cap) — while the round-2 provider response is still in flight on a slowly-streaming stand (`--delay-ms 4000`). The cancel is issued only after the marker is observed. Typed REQUESTED cancel settle is asserted: `cancelAck status=accepted`, terminal `cancelled/incomplete`, `cleanupStatus=complete` (closed workspace), adapter exit 26, `run.json` exitCode 26 / status `Cancelled`. This is the distinction from the frozen `cancel-mid-run`, whose cancel lands BEFORE the first provider round-trip returns (no provider response consumed, no tool executed, no marker).
- `cancel-late` (adversarial distinction): the cancel frame is written only AFTER the terminal `completed/success` frame has been consumed. The adapter closes ordinary input at the terminal (no reply is owed; write errors tolerated honestly), and the settle must stay completed: adapter exit 0 (a REQUESTED cancel would exit 26), `run.json` exitCode 0 / status `Succeeded`. The fixture therefore distinguishes "cancel too late" from the mid-run typed cancel at three levels: consumer exit code (0 vs 26), `run.json` status (`Succeeded` vs `Cancelled`), and independent-checker assertions for both.

New standalone driver `contracts/acceptance/cross-ecosystem/llm4s-consumer/run-cancel-mid-response.sh`: reuses `scenarios/lib.sh` read-only (compile_all, start_stand, run_llm4s, stop_stands with the RAI-229 stop policy), runs a fast stand for one genuine frozen `tool-task` setup run (so the checker's workspace section asserts really produced evidence), a 4000 ms slow stand for the two new scenarios, then the independent checker against the new frozen golden. New frozen golden `contracts/acceptance/cross-ecosystem/expected/cancel-mid-response-golden.json` (id `XE-242-cancel-mid-response`, `adapterJarSha256 997f29a18e38848c082deaeb825a7f4da40ca76d47444663c656693a16d47fdd`, same verified jar as `XE-205-golden-checks`; format mirrors the frozen golden exactly).

**Wiring deferral (disclosed).** `run-all.sh` / `run-budget.sh` / `lib.sh` are NOT modified, and the corpus checker still validates exactly the frozen 20-entry `expected/golden-checks.json`. Wiring the new scenarios into run-all is not purely additive: it would require editing the `run_checker` manifest list in `lib.sh`, the scenario lines in `run-all.sh`, and adding entries to the FROZEN `expected/golden-checks.json` (a non-goal: no change to existing frozen expectations). The consumer registry (`validScenarios`/`isStandScenario`) growth is inert for the corpus because run-all never requests the new scenario names.

RAI-238 owns the run-all/run-budget wiring; when wiring lands, `expected/golden-checks.json` must grow the two entries under a card that may lawfully touch it (the standalone golden `XE-242-cancel-mid-response` is written so its scenario entries can be transplanted verbatim).

The recorded EXECUTE run is the only verdict; it passed within the frozen gate budgets with `timeout=False` on every gate. No gate was skipped or lowered.
- The missing-stand case settles in ~24 s (20 s bounded marker poll + typed failure), not instantly; the bound is client-side and finite. If RAI-238 wants faster diagnosis, the consumer could abort the marker poll when the adapter process dies — deliberately not changed here (would alter check semantics mid-card).
- The concurrency harness is a temp script (`/var/folders/.../rai-242-logs/conc-iter.sh`), not committed: it copies fixture class dirs per iteration to avoid `compile_all` write races and stops its stands by pid with a bounded wait. It does not use `stop_stands`' pidfile lifecycle, hence the disclosed stale-pidfile cleanup. lib.sh itself is untouched.
- `cancel-late`'s probe assertion is indirect by protocol necessity (ordinary input is closed at the terminal; no cancelAck/refusal reply is owed): the settle assertion is the adapter exit code + `run.json` status + checker artifacts section, with the write-success check recorded honestly (`late-cancel-probe-sent`).
- Evidence directories under `artifacts/**` are untracked build/evidence outputs; the record pins the durable hashes. Temp logs are volatile per the platform temp policy.
