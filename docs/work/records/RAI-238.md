## Resulting behavior

Both drivers (`contracts/acceptance/cross-ecosystem/scenarios/run-all.sh`, `run-budget.sh`) now install crash-path cleanup (identical 21-line block in each):

- `trap xe_cleanup EXIT` — on every exit path, including a `set -e` abort after a failing consumer run (the RAI-229 §Limitations crash-path leak gap), `xe_cleanup` runs a best-effort `stop_stands` so no started stand is leaked.
- `trap 'exit 130' INT`, `trap 'exit 143' TERM` — signal exits convert to the conventional codes, which the EXIT trap then augments with cleanup.
- `xe_cleanup` captures `rc=$?` first, resets the traps, runs `stop_stands || stop_rc=$?`, and on a stop failure logs `WARN: EXIT-trap stop_stands failed (rc=$stop_rc); preserving original exit code $rc` before `exit "$rc"`. A cleanup failure is diagnosed and never masks the driver's original exit code (verified interactively with a planted foreign pidfile: identity-guard refusal + WARN + original code preserved).
- No double-kill: the normal path already stops stands and removes pidfiles, so the trap's `stop_stands` is a no-op (`stop_stands: no stand pidfiles or registered pids found (nothing to stop)` — visible in every official green run log).

## Limitations / blockers

- TERM delivery is deferred until the current foreground `java` consumer completes (observed: the in-flight llm4s-mock manifest finished before the trap cleaned up; exit 143). Worst-case cleanup latency is therefore bounded by the in-flight consumer run, not instantaneous. Making TERM preempt the child would require running consumers as tracked background jobs with orphan-kill bookkeeping — deliberately not done (larger diff, more review surface; the card asked for crash-path cleanup, not a process supervisor).
- INT arming caveat (pre-existing bash property, disclosed): when a driver is started as an async `&` job of a non-interactive job-control-less shell, SIGINT is SIG_IGN at exec and the INT trap cannot arm — an INT then never aborts the run and it completes normally (cleanup via the normal path; no leak). All real invocation forms (interactive terminal, `make`, CI) start drivers in the foreground, where the trap arms and fires promptly (proven by the faithful Ctrl-C drill). My first INT drill hit exactly this harness artifact, which cost one absorbed run (`sigint-run.log`, run completed green 20/20 with cleanup) before the mechanism was understood.
- A second signal arriving during cleanup takes the default action (`trap - EXIT INT TERM` resets before stopping), so the driver can die mid-cleanup; `stop_stands` pidfiles are durable and a later sweep reaps, but cleanup itself is not signal-protected (out of scope).
- The budget driver's INT/TERM paths were not separately drilled; they use the identical trap block, and the official budget run exercises the normal path plus the trap no-op.
- Manual reaps disclosed: RED-drill leaked stands (70588/70607) and the warn2 foreign `sleep 900` (75605).
- `observe-dedup` flaked once under load (~31; `warn-run.log`) — pre-existing flake family (RAI-229 saw it at load ~313); reruns green; unrelated to this diff.
- Scratch evidence under `/var/folders/...` is volatile; the sha256 values above are the durable references.
