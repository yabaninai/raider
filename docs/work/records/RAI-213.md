## Resulting behavior

`PortableChatExport.exportTo` now distinguishes the staging-race loss inside `writeStaging`: when `Files.createDirectory(staging)` fails with `FileAlreadyExistsException` (the check-then-create window against a concurrent winner, or an obstruction that appeared after the freshness pre-check), the export refuses typed `CWF-R5` with message prefix `staging claim lost: … refusing WITHOUT deleting it` and does NOT delete the existing staging directory. The `NonFatal` catch-all keeps its previous behavior (best-effort cleanup of THIS attempt's own staging). Net effect: exactly one concurrent export publishes; the loser refuses typed with the winner's in-flight staging intact — the two exports can no longer destroy each other through the shared cleanup path.

The class Scaladoc no longer claims that "concurrent exports to the same target serialize on the fixed staging name"; it now states the fail-fast exclusion discipline (one winner publishes; the loser's `createDirectory` fails with `FileAlreadyExistsException` and refuses WITHOUT deleting; RAI-213; ADR-033 §6.2/§9.1).

Two tests added to `PortableChatExportSpec`:

1. Deterministic pin (no visibility seam; `writeStaging` stays `private`): a dangling symlink at the staging path passes the `Files.exists` freshness pre-check and forces `FileAlreadyExistsException` inside `writeStaging`. Asserts the typed refusal contains `CWF-R5`, `staging claim lost` and `WITHOUT deleting`, the symlink staging is intact, and nothing was published.
2. Latched two-thread race, 30 iterations (latches, not sleeps): two threads released by one `CountDownLatch` run full `exportTo` calls to the same target on a 2-thread pool; per iteration, filesystem facts are captured after both threads join: exactly one `Right`, the loser is `Left` with code `RA-INP` and `CWF-R5` in the detail, the parent contains exactly `out` (no staging remnant), `out` contains exactly the three artifacts byte-identical to the pure re-render, and the winner's digests match `sha256Hex` of the rendered document/input bytes.

## Limitations / blockers

- **`sbt-test` gate has no green execution — concrete blocker, verbatim:** three `make quality-changed QUALITY_EXECUTE=1` runs, `sbt-test: failed exit=1 timeout=True` each time (900 s registry cap, `scripts/quality-policy/registry.json` `gates.sbt-test.timeout_s`). Root cause measured on this host: 18 logical CPUs with load averages up to `226.42` (1-min) / sustained `96–178` from sibling lanes (`wt/rai-187`, `wt/rai-211`, `wt/rai-212` running their own suites concurrently); a warm, un-contended `sbt --batch test` succeeds in `1105 s`, which alone exceeds the 900 s cap. No test failure was observed in any attempt — every suite logged green up to each kill. Gate policy is protected; it was NOT modified (a timeout is not a pass, and thresholds are not lowered or bypassed). The registered remedy is **RAI-209 "Raise the sbt-test gate timeout under host contention"** (900 s → 1800 s, owner authorization 2026-10-26) — a separate card for the policy owner's lane. Until RAI-209 lands (or a quiet window occurs, load < ~40), a green `sbt-test` execution of this tip is pending; the closest substitute evidence is the manual full-suite `sbt --batch test` success (exit 0) on the identical source state.
- The manual warm full-suite run and the third gate execution ran under residual contention; per-suite timings in those logs are not representative baselines.
- First bootstrap needed `SSL_CERT_FILE` (certifi) because macOS framework Python 3.12 urllib has no default CA bundle; bootstrap.sh itself was not modified. This may bite other lanes; worth a runbook note.
