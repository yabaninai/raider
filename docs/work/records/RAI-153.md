## Resulting behavior

The loop can now emit the ADR-032 v2 phase payloads LIVE at phase boundaries
the runtime genuinely knows, into the RAI-144 multi-job export stream:

1. **Emission seam (`LoopEvents`, runtime).** New optional `phases:
   Option[LoopEvents.PhaseSink]` on the per-run emission context (default
   `None` = literal no-op, zero overhead) with two methods,
   `phaseStarted(name, recovery, note)` and `phaseFinished(name)`. The channel
   is LINEAGE-WIRE-ONLY: phase records never touch the frozen ADR-024 hub
   (the 13-case `EventPayload` family and its readers are untouched) because
   ADR-032 §1 already versioned the wire — this card populates the existing v2
   revision live. Seam hygiene: an empty `name` is dropped at the seam (the
   wire refuses empty names at decode — an undecodable stream is never
   produced); names travel verbatim (no truncation — `phase_finished` closes
   by name, a truncated name would lie); `recovery` is the closed LINEAGE
   taxonomy (`raider.runtime.lineage.model.RecoveryClass`:
   `ReadOnly|Idempotent|Mutating`), not the same-named `raider.core` tool-axis
   enum; emission is failure-absorbing like every other `LoopEvents` surface.

2. **Real loop boundary (`AgentLoop.runPlan`).** The ONE phase boundary the
   runtime tracks — the plan phase (RAI-107 §2) — now emits
   `phase_started("plan", ReadOnly)` before the first plan attempt and
   `phase_finished("plan")` on EVERY exit (success, typed `PlanRejected`,
   cancellation — the `onExit` finalizer runs uninterruptibly). Bounded repair
   attempts stay INSIDE the one `plan` phase (PLAN-01 semantics; no separate
   repair phases are invented). Ordinary `runText` emits NO phase records: the
   runtime tracks no other stage semantics, and none were invented (card
   non-goal).

3. **Exporter sink (`MultiJobExport.phaseSink`, CLI).** The exporter implements
   `LoopEvents.PhaseSink`: it builds the v2 envelope (campaign job id,
   `schemaVersion: 2`, export-canonical per-job `nextSeq`, caller-supplied
   root/session/atMs verbatim, no `invocationId` on root-job v2 envelopes per
   ADR-032 §1) and appends it through the SAME export lock as every other
   line, so file order and the fold buffer stay one sequence. Ordering
   discipline: BEFORE the locked append the sink settles the campaign's own
   hub stream (`EventExport.awaitCaughtUp` over `campaignWritten`, bounded
   best-effort) — every campaign envelope published before the phase call is
   in the file first, and any envelope published after the call can only be
   appended by the single collector fiber after the phase line (the emitting
   fiber is blocked on the call). Phase lines do NOT count into
   `campaignWritten` (not hub envelopes), so the settle watermark stays exact.
   A phase emitted before the campaign job is known is dropped, never
   invented; an append defect absorbs at this seam (the unwritable environment
   still fails the run through the main export path).

4. **HeadlessRunner wiring (RAI-144 path).** The campaign job's `LoopEvents`
   now carries `phases = Some(join.phaseSink)`; child jobs keep the default
   sink-less context (their v2 envelopes would require the correlation key;
   delegation children emit no phases today — documented limitation). A
   product CLI target that opens plan phases does not exist yet, so the
   end-to-end product path is exercised at the loop level and the exporter
   level (below), not by a `raider run` CLI scenario.

5. **RAI-145 fixture flipped to live emission (stand-in retired).**
   `UnifiedProjectionExecutionSpec` no longer post-hoc inserts phase
   envelopes (`enrichAndWrite` and the seq renumbering are DELETED). The
   scripted campaign emits its five stage phases through the SAME product
   surface — the exporter's `phaseSink` on the campaign's own `LoopEvents` —
   enter before each stage's fork, exit after the stage's last child joined.
   The reduction input is the REAL `events.jsonl` exactly as the exporter
   wrote it (read back through the versioned reader, replay discipline;
   round-trip against the fold buffer asserted). The reduced graph, the 23-
   report executed tree, fan-out lines and hash pins are unchanged; the
   generator needed ZERO changes (emission-agnostic, ADR-032 §6). UNI-01/
   UNI-02/UNI-03a/UNI-03b stay green, including the detached-boundary shape
   (the boundary phase closes after the detached member's last scripted line
   joined).

### Emission-point table

| Boundary | Who knows it | Emission | Payload on the wire |
| --- | --- | --- | --- |
| Plan phase enter (before attempt 1, after typed-refusal preflight) | `AgentLoop.runPlan` (RAI-107 §2) | `LoopEvents.phaseStarted` | `{"type":"phase_started","name":"plan","recovery":"ReadOnly"}` (v2, campaign job) |
| Plan phase exit — success / typed rejection / cancellation | `AgentLoop.runPlan` (`onExit`) | `LoopEvents.phaseFinished` | `{"type":"phase_finished","name":"plan"}` (v2, campaign job) |
| Plan repair attempts (inside the phase) | `AgentLoop.planAttempt` | none (no separate marks) | covered by the single `plan` phase |
| Ordinary `runText` rounds | `AgentLoop` | none | — no phase semantics the runtime tracks |
| Scripted application campaigns (fixture BillingCi stages; any future caller that tracks its own stages) | the CALLER's own loop | `phaseStarted`/`phaseFinished` | v2 stage phases through the same sink |

## Limitations / blockers

- **JDK toolchain incident (environment, not code).** sbt's JVM autodetection
  picked a Homebrew JDK 27 in this lane's first gate attempts; a FRESH compile
  of the untouched baseline file `AgentLoop.scala` fails there with a bogus
  `E008: value id is not a member of raider.core.ToolCall` (the classfile
  carries the `id` alias; the same sources compile clean under the repo's
  pinned JDK 21 — see `docs/working-product.md` "JDK21"). All evidence above
  is JDK 21. Root warm targets never re-typecheck that file, which is why the
  integration build never saw it. A toolchain-pinning follow-up (sbt
  `--java-home` or gate-runner JAVA_HOME enforcement) is recommended — a
  clean-checkout full build under JDK 27 will fail for everyone.
- **Pre-existing timing-sensitive specs flaked twice under back-to-back
  full-suite load, on tests this card does not own:** MJE-03c
  (`MultiJobExportSpec`, RAI-144 — child-join vs campaign-settle race:
  failed once in manifest `20261014-000619-14543-0001`, green 3/3 standalone
  and in the other full-suite runs) and PLANUI-02 (`PlanPanelSpec`, RAI-110 —
  failed once in manifest `20261014-001303-21595-0001`, green 3/3 standalone).
  Both passed on the SAME fingerprint in the final runs
  (`20261014-002333-37004-0001`, `20261014-003206-46292-0001`,
  `20261014-003623-49136-0001`) and on the stashed baseline. Earlier failed
  manifests from this lane, kept for honesty: `20261013-233320-54741-0001`
  (JDK-27 compile + pre-format scalafmt), `20261013-235556-2142-0001`
  (scalafmt, fixed by formatting). No threshold was touched; a hardening card
  for those two wait-disciplines is a candidate.
- **Child-job phase emission is deliberately not wired.** v2 envelopes of a
  non-root job require `invocationId` (ADR-032 §1); delegation children are
  plain `runText` loops with no phase semantics, so their `LoopEvents` stay
  sink-less (default `None`). Wiring child phases belongs to the delegation
  follow-up (RAI-154 territory), not this card.
- **No product CLI target opens a plan phase today**, so the HeadlessRunner
  wiring is exercised at the loop level and exporter level (the acceptance
  fixtures), not by a `raider run` scenario. The wiring point is exactly the
  RAI-144 export path; when a plan-phase CLI target lands, emission flows
  without further changes.
- The card's allowed-path `docs/adr/ADR-024-events.md` does not exist (the
  frozen seam ADR is `docs/adr/ADR-024-runtime-ui-event-seam.md`). The frozen
  ADR was NOT edited: this card changes nothing in the frozen seam (the
  emission contract is documented in the `LoopEvents.PhaseSink`/`AgentLoop`
  scaladoc, the living emission-point documentation of this repo), so no ADR
  revision is required.
