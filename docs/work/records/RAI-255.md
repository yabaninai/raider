## Resulting behavior

`quality verify` no longer accepts manifests that attest nothing or attest a toolchain that was not the verifying environment (card `docs/tasks/m1.md` RAI-255; audit findings in `docs/reviews/2026-11-01-readiness.md`):

1. **Zero executed gates** are rejected on every schema version with the diagnostic "manifest records ZERO executed gates — it cannot attest any quality profile". The audit's synthetic manifest (real fingerprint/policy hashes, `profiles: ["fast"]`, `gates: []`, `toolchain: {}`) was previously accepted with exit 0; it is now rejected.
2. **Gate-set completeness (schema_version >= 2):** a manifest claiming profile P must contain every gate the current registry requires for P; each missing gate is named together with its claiming profile(s) (e.g. `'sbt-compile' required by ['fast']`). Unknown claimed profiles are rejected. Schema-v1 manifests are exempt from completeness (the `fast` profile grew after those manifests were produced) but still require at least one gate.
3. **Structural gate validation (v2):** registry-known gate ids, no duplicate ids, argv equal to the registry, `status`/`exit_code`/`timed_out` mutually consistent (`timed_out=true` is an independent rejection — a timeout is never a pass), `duration_s` present and non-negative, gate log present and hash-matching.
4. **Toolchain identity:** the manifest toolchain must record established `java`, `sbt` and `scala` identities on all schema versions. In strict verify (no `--allow-stale`) they must equal the verifying environment's `java -version` / `sbt --version` snapshots; a missing local tool is a fail, never a skip. `--allow-stale` keeps the historical semantics: presence required, identity comparison skipped. `python3` is recorded but deliberately not identity-compared.
5. **Malformed manifests** (not JSON, non-object root, missing fields) are rejected with precise diagnostics instead of `KeyError` tracebacks, and the OK message no longer claims "toolchain hashes checked" that never happened.

Migration note (documented in the module docstring): manifests produced before RAI-255 verify unchanged when coherent; historical verification of old manifests still works via `--allow-stale` when the policy hash matches and the toolchain identity was recorded. Compatibility check basis (quality manifests are gitignored, so this was an artifacts survey, not a git sweep): every schema_version-2 quality manifest present in the root checkout's `artifacts/quality/` on 2026-11-01 was enumerated and checked against the current registry profile sets — all complete (missing=NONE); schema-v1 manifests from 2026-10-03..05 predate the grown `fast` profile and rely on the documented v1 exemption. No manifest format, gate, threshold, or profile change: the runner (`execute`) writes exactly the same v2 shape as before.

## Review fix (2026-11-01, APPROVE-WITH-REQUIRED-FIX)

**Finding (reviewer, independently reproduced on `fcaa358`):** the schema-v1 lenient gate path in `_gate_verify_problems` false-accepted fabricated gates. `log = ROOT / str(g.get("log", ""))` resolved a missing `log` to ROOT itself (exists → no "log missing" problem) and the hash check was skipped when `log_sha256` was absent. The base verifier crashed on such inputs (KeyError → exit 1), so lenient acceptance was a false-accept regression of the exact audited defect class:
- Probe A: v1 manifest, profiles `["fast"]`, fresh legacy_inventory fingerprint, current policy hash, matching toolchain, gate `{"id":"sbt-test","status":"passed"}` → exit 0 (WRONG).
- Probe A2: same + `"log":"README.md"` without `log_sha256` → exit 0 (WRONG).

**Fix (minimal, reviewer-specified):** in the v1 branch both `log` and `log_sha256` must be non-empty strings; each missing field is named independently (`gate sbt-test log field missing — a passed gate must reference its run-time log (fabricated gate)` / `gate sbt-test log_sha256 missing — a passed gate must bind its run-time log hash (fabricated gate)`), mirroring the old KeyError semantics with proper diagnostics. Real v1 manifests wrote both fields, so historical compatibility is unaffected (the v1 historical positive control still passes). An initial draft used `continue` after the first diagnostic and was caught by the new self-check case itself (a gate missing both fields printed only one diagnostic); both fields are now reported independently.

## Limitations / blockers

- `python3` toolchain identity is recorded but not compared in strict mode (deliberate: not part of the product toolchain identity per the card). This is documented in `_toolchain_verify_problems`.
- Gate argv equality is checked against the current registry verbatim; a registry argv change therefore invalidates older v2 manifests (policy_sha256 already rejects those runs; argv checking is defense in depth). Exact argv-equivalence normalization is out of scope for this card.
- Self-check runtime grew from ~1.7 s to ~59 s (verify subprocess battery); still under the frozen 120 s `self-registry-check` budget, but the margin shrinks on a contended host. If it becomes tight, a separate policy card can split the battery.
- The red-fixture `.out/.err` evidence files live under `artifacts/` (gitignored) and are cited by path; they are not part of the committed fingerprint.
- Independent review of this protected-verifier change is required before merge (card contract); lane evidence does not replace checking the integrated candidate.
