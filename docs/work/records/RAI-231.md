## Limitations / blockers

1. **Load-sensitive `observe-dedup` race in the integrated candidate (inherited, not caused by this card; recorded verbatim).** In `run-all.sh` (attempts 1 and 2) and in a targeted block-shape loop (`--scenario refusals,observe-dedup`, one consumer JVM, 2/6 iterations failed), the langchain4j mock `observe-dedup` scenario intermittently failed `sequences-strictly-increasing` and `no-duplicate-frames-after-dedup` with observation sequences `[2, 3, 4, 5, 6, 1, 2, 3, 4, 5, 6]`, `[2, 3, 4, 1, 2, 3, 4, 5, 6, 5]`, and `[2, 3, 4, 1, 2, 3, 4, 5, 6]` (live frames leaking ahead of the replay instead of being suppressed). Eight cold-JVM standalone runs of the same scenario passed 8/8, so the trigger is the timing of `observe(afterSequence=0)` arriving while the live forwarding pump is still emitting. Adapter-side pointer (read-only): `modules/cli/src/main/scala/raider/cli/processapi/Session.scala`, `private def observe` replays `retention` filtered by `seq > afterSequence` while the live path writes the same outbound channel without coordination. The card has zero product deltas and runs the canonical integrated jar, so this is an inherited product concurrency gap. Fixing it would change the adapter jar and is outside this card's allowed paths; a follow-up runtime-concurrency card is recommended (per contributor rules it must carry cancellation/ownership/budget tests). The official green run (attempt 3) passed 20/20 with checker `failed=0` under 1-minute load averages of 290–324 on an 18-core host (foreign VM cycling; load readings recorded at 14:20–14:47 local). No threshold or verifier was changed to obtain green.
2. **Adapter jar rebuild nondeterminism.** A fresh `make raider-jar` from byte-identical sources (same commit `531d57c`, clean worktree, `modules/**` untouched) produced `24256330c2d8909cc7cce5f14fc7b37557d8f8db64cf02c14683ec418f99fa43`. Forensics: 13114 jar entries, identical entry name sets, 105 entries (53 `.class`, 52 `.tasty`) with differing CRCs — compiler/assembly nondeterminism, not a source difference. Consequence: jar-hash invariance across rebuilds is not achievable in the current build; the card's evidence is therefore bound to the canonical integrated jar (`997f29a1…`) copied read-only from the root checkout into the worktree path that `scenarios/lib.sh` resolves (`$ROOT/modules/cli/target/scala-3.9.0/raider-cli.jar`). A reproducible-build card (assembly timestamp canonicalization) is recommended.
3. **Environment provisioning (gitignored, disclosed):** `artifacts/tools/m2` copied from the root checkout (62 jar files, 114M); the pinned consumer closure was verified — all 31 `consumer-deps.json` entries match sha256 and size. `artifacts/xe-out` had to be created manually before the first `run-budget.sh` invocation on a fresh worktree (the driver assumes the shared-out directory exists; first invocation failed at `lib.sh` line 52 with `stand-C.log: No such file or directory`, recorded in the console capture). Both points are worktree-local setup, not repository changes.
4. The m2 closure verification script first reported spurious MISSING entries because it double-prefixed the already-repo-relative `path` values in `consumer-deps.json`; corrected verification: 31/31 OK.
5. `docs/tasks/backlog.json` and the board are not in this card's allowed paths; board updates are the coordinator's.
