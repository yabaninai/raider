## Resulting behavior

**Pinned naming decision** (the card offered a choice; this is the pinned
scheme and why):

- BEFORE (RAI-155.c renderer, defect found by RAI-155.d): `object <Name>` +
  `@main def <name>` with `<Name> = capitalize(slug)`, `<name> =
  decapitalize(slug)`. dotc emits `<Name>.class` + `<Name>$.class` and
  `<name>.class` — a case-mirror pair that overwrites itself on a
  case-insensitive filesystem (macOS default), nondeterministic write order,
  nondeterministic produced classes (RAI-155.d finding 1). Digit-leading
  slugs were worse: capitalize/decapitalize are no-ops there, so the pair was
  a double definition.
- AFTER (this card): `object <Capitalized slug>` (UNCHANGED) + `@main def
  run<Capitalized slug>` (renamed with the `run` prefix).
  - The object name CANNOT change: the CLI run path
    (`WorkflowBuildIdentity.deriveClassNames`, immutable for this lane)
    derives the module class `<Capitalized stem>$` from the source-file stem
    and `WorkflowRun` loads the generated object reflectively by that name;
    renaming the object would break `raider workflow run` from files this
    lane may not touch.
  - The `run` prefix makes the @main class case-insensitively distinct from
    every other emitted class for ANY slug: the emitted top-level files are
    `<Cap>.class`, `<Cap>$.class`, `run<Cap>.class` — pairwise distinct
    ignoring case (`run<Cap>` is longer than every mirror; equality ignoring
    case is impossible). The digit-leading double-definition is also gone.
  - The Program label stays `<decapitalized slug>-workflow` and the default
    input path is now exactly the §6.2-published `<slug>.input.json` (the
    previous code derived it from the old `mainName`; the referent had to
    move when the main was renamed — byte-identical output for every
    lowercase slug, §6.2-coherent for uppercase-initial slugs).
- The golden example (`examples/chat-workflow/fix_widget_task/`) was
  REGENERATED THROUGH THE PRODUCT PIPELINE (never hand-edited): a throwaway
  harness (`raider.dsl.workflow.RegenerateGoldenExample`, deleted before
  commit) removed the previous generation and re-exported via
  `ChatWorkflowExport.exportTo` (the §6.2 staging + atomic-rename
  discipline). Diff: exactly one line in `fix_widget_task.scala` (the @main)
  and the pipeline-computed `sourceDigest` pin in the manifest:
  `sha256-f9cf0b8d…` → `sha256-405dcd27…`; `specDigest` unchanged
  (`sha256-97bf8c34…`, selection untouched); input example byte-identical.
  This is the RAI-146 discipline: pins are pipeline outputs, updated by
  regeneration.
- The .c compile gate (`ChatWorkflowCompileGateSpec`) now carries **WNF-01**:
  after the pinned-dotc compile of a fresh render it (a) reads the FULL dotc
  log and requires ZERO `differs only in case` warnings (the RAI-155.d defect
  warned without failing compilation — exit codes alone can never catch it),
  (b) runs an exact-case tripwire over the produced classes (no two `.class`
  files collide ignoring case — the WorkflowCompile exact-case-scan
  discipline; a naive `Files.exists` false-positives on this filesystem),
  and (c) LAUNCHES the compiled `runCwf_gate_probe` @main entry as a plain
  main in a child JVM with a missing input path, asserting exit 1 with the
  typed `raider RA-INP` line — the exact local-plain-main leg RAI-155.d found
  unreliable under the collision. A class collision now fails at GATE time,
  not at first user launch.
- WNF-02 unit pin (`ChatWorkflowRendererSpec`): the rendered top-level pair
  is deterministic (render ×2 byte-identical) and case-insensitively distinct
  over a representative slug set — lower-first, mixed case, all-caps, a slug
  already starting with `run`, and a digit-leading slug (the old scheme's
  double-definition shape) — pinned black-box over the rendered source text.
- The .d spec suites no longer carry the collision workaround:
  `WorkflowCompileSpec` (D01/torn/stale) and `WorkflowRunSpec` compile the
  UNEDITED render; `WorkflowLaunchSpec` launch A runs the real
  `runWf155d_launch` (the baseUrl editable-constant edit remains, as the
  CWF-D01 edit-survives-compilation surface). `WorkflowCompileSpec` review
  fix 2c recreates a REAL `<stem>` main by fixture edits (rename the @main
  onto the derived stem, move the object token out of the case-mirror) to
  exercise the collision detector's positive branch through the public
  entry — post-fix the as-is build emits no `<stem>.class` at all, so the
  fixture is the only way to reach that branch with a real matching main.

## Limitations / blockers

1. **Stale references to the old pair shape — CLI/doc owners (outside this
   lane's paths), contract-change follow-ups:** (a) `docs/adr/ADR-033-chat-workflow-export.md`
   §6.3 sketch (lines ~277/296: `object <Name>` + `@main def <name>`) — the
   rendered shape is now `object <Name>` + `@main def run<Name>`; (b)
   `WorkflowBuildIdentity.deriveClassNames` doc comment still describes the
   `@main def <stem>` pair; (c) the frozen build-identity `mainClass` field
   records the STEM-DERIVED name (`wf155d_probe`), which is now metadata
   only — the emitted launcher class is `run<Cap>` — so a consumer that
   java-launches `identity.mainClass` directly would target a nonexistent
   class. The RUN path consumes only `moduleClass` (verified: `WorkflowRun`
   reflective loads use `identity.moduleClass` and the module's nested
   classes; `mainClass` feeds `verifyMainNotCollided`'s exact-case scan,
   which correctly early-outs when the stem-named file is absent). Required
   one-line CLI change (separate card, CLI main files): derive `mainClass` =
   `run<Capitalized stem>` (+ comment fix). This card cannot touch those
   files.
2. WNF-01's launch-the-main leg asserts the typed missing-input failure
   (exit 1, `raider RA-INP`) rather than a full successful launch: a green
   launch would need credentials and a live provider stand inside the .c
   gate (paid-call/mocking boundaries). The full green launch of the
   generated artifact against a LOCAL scripted stand is proven by
   `WorkflowLaunchSpec` CWF-D01 (launch A, exit 0, real tool effects, 4/4
   auth'd model rounds) — now on the UNRENAMED `runWf155d_launch`.
3. The `decapitalize`-derived Program label and default-input path keep the
   lowercase-slug output byte-identical; the default input path changed only
   for uppercase-initial slugs, where it now names the file §6.2 actually
   publishes (previously it named a file the export never wrote on
   case-sensitive filesystems).
4. The `examples/chat-workflow` golden is compile-covered indirectly (the .c
   gate compiles a byte-identical fresh render), not as a file; unchanged
   discipline.
5. No ADR was drafted by this lane: the card is the coordinator-accepted
   contract change from RAI-155.d's request; the ADR-033 §6.3 text update
   belongs to the docs owner (limitation 1a).
