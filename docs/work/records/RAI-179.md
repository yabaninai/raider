## Resulting behavior

`raider workflow run` now accepts launch-time `--checkpoint <id>:<scope>`, optional `--approval-request <path>`, and `--decision-file <path>`. The declaration is a pause gate, not a permission grant; workflow definitions remain unchanged. The launcher derives a candidate digest from the verified compiled workflow, current input, and actual workspace tree. A request invocation writes the RAI-165 approval request under `--out` (or the explicit artifact path) and returns exit 25 before dispatch. A new invocation reads the existing request and decision, binds the decision to the same checkpoint/digest/expiry, and re-reads compiled-build/input/workspace state before dispatch. The accepted dispatch is checked again immediately before the workflow program is invoked. Changed state and expired/invalid decisions return typed nonzero refusals. CLI JSON status is `needs-approval` for exit 25.

The only authority used is the existing capability to run the workflow that the owner explicitly invoked; checkpoint scope affects the candidate policy identity and cannot create or broaden that capability. No continuation, fiber, or workflow state is resumed.
