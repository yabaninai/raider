## Limitations / blockers

1. **Machine/toolchain scope of the pin.** The pinned hash is measured on this host/toolchain (macOS/darwin, Java 21.0.12.1, sbt with COURSIER_CACHE=/tmp/cc-master, Scala 3.9.0 per the pinned closure). A different toolchain is not claimed to reproduce these bytes; the card's requirement is two clean rounds on the integrated candidate, satisfied.
2. **Make target vs direct script.** `make repro-jar` (RAI-251) takes no arguments, so the `--out` evidence path went through `scripts/repro-jar` directly. This is the same sbt stage (`sbt --batch raiderCli/assembly`) plus the same canonicalizer; the script itself sets `COURSIER_CACHE=/tmp/cc-master`, the same default as the Makefile target (verified in `scripts/repro-jar`, `run_sbt`).
3. **Load discipline deviations, disclosed.** The RAI-240 policy (bounded 120 s sleep when 1-min load > 12) was not able to bring the host below 12: a foreign Virtualization VM churned the shared 18-core host at 1-min load 86–246 throughout the session (baseline `246.5/222.3/200.7`). All sbt invocations and all corpus runs proceeded under this foreign load, with readings recorded per run in the evidence files (embedded in logs, per the RAI-230 lesson). Precedent: RAI-240 gates green at 91–122; RAI-240 corpus green at 122.5; RAI-233 greens at 4–22. No gate, threshold, or timeout was modified.
4. **Probe-level load-timing misses in the load generator (not adapter regressions), disclosed verbatim.** Of 778 probe invocations (730 with recorded rc lines), 46 worker invocations exited nonzero: 34 dedup-probe invocations (35 individual `observations-nonempty FAIL sequences=[]` misses; one invocation was killed by the run-end cleanup before printing its rc line) and 12 cancel-probe invocations (15 individual in-batch iterations with `terminal=failed` instead of `cancelled`). Classification: at aggregate 1-min load 87–190 the dedup probe's 30 ms hold window stretches so far that the entire mock stream drains before `observe(afterSequence=0)` lands; the coordinated adapter then correctly returns no already-delivered frames (`observe_failed`/empty replay is the frozen tolerated behavior, README "Treat observe_failed … as tolerated"; RAI-233 record documents the same suppression). The probe's non-empty expectation assumes a mid-stream replay and is load-sensitive. The failure that matters — frame duplication — never occurred: `no-duplicate-frames-after-dedup` and `sequences-strictly-increasing` passed in every one of the 730 iterations, and the frozen consumer-level corpus checks passed 6/6. The cancel-probe misses are the same class (cancel-vs-terminal timing under load inside the probe's own 10-iteration batch); the frozen corpus `cancel-mid-run` scenario passed 6/6. Probes remain lane load-generation tooling (never registered as gates); no probe or golden was modified.
5. **Placement step disclosed.** The corpus consumes the jar from the binding path; the canonical jar was placed there via `--from-assembly` (idempotent canonicalization, output hash identical to the measured rounds). Raw-keeping (`raider-cli-raw.jar`) is not used on this lane (RAI-252 P3-4 known defect, routed to a script-hygiene card).
6. **Interrupted gate attempt, disclosed.** The first `make quality-profile PROFILES="fast contracts"` attempt was terminated by the session tool's 10-minute foreground timeout (SIGTERM to `make`); it wrote no manifest (directory `artifacts/quality/20261101-022106-17776-0001/` contains no `manifest.json`) and no result is claimed from it. The completed re-run (`20261101-023115-27279-0001`) supersedes it. No threshold, timeout, or check was modified to obtain the green.
7. **Checker classification of the sibling driver.** `cancel-mid-response-golden.json` is validated only by the standalone driver (run-all wiring deferred to RAI-238 per the golden's own description); the driver run above is the evidence, not part of the 20-scenario corpus count.
8. **Record/manifest ordering.** This record was written before the gate runs (the runner validates records); the manifest ids and sha256 values above were filled in from the executed manifests afterwards — a record-only, operational edit under the exclusion policy; no product-input file changed after the gate runs (the two golden pins were edited before every gate and corpus command above).
