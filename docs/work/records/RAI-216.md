# RAI-216: Bounded finalization for the generated check runner

Status: done (card scope complete on this lane tip; renderer/golden path deviation disclosed below and pending coordinator ratification at integration review). Date: 2026-10-26. Baseline: `b90a191` (`lane/rai-216`, worktree `wt/rai-216`).

## Resulting behavior

The generated check runner (emitted by `ChatWorkflowRenderer` into every exported workflow, including the `fix_widget_task` example golden) no longer joins its check-output drain unboundedly:

- Both drain joins (`stdout`/`stderr` readers) are bounded by the check's finalization bound. If a reader is still alive when the bound elapses, the partial output captured so far is retained, the remaining case state is typed as a bounded-finalization outcome, and the case is marked failed. The check process is destroyed (or already interrupted) as before; the runner never hangs on a grandchild holding the pipe.
- The captured-check-output JUnit detail embeds a truthful cutoff note for the natural-exit bounded path (`cut off by the <bound>s finalization bound` plus the captured byte count, `bytes captured before the cutoff`) and the existing destroyed note for the destroyed path (`exceeded the <bound>s bound and was destroyed`). The pre-existing 65,536-byte capture cap is unchanged (introduced in RAI-186).
- Ordinary runs (no pipe-holding grandchild, check exits cleanly) are byte-for-byte the previous behavior apart from the bound, which only engages on the previously hanging path. SIGTERM/143 semantics are untouched: product-side `Main.scala` shutdown hook, `WorkflowRun` interrupt guard, and interrupted-marker writing were inspected and required no change.
- New acceptance spec `raider.cli.run.Rai216BoundedFinalizationSpec` proves the behavior with real CLI child processes and real grandchild processes holding the output pipe (no mock interpreter for the pipe behavior): bounded natural exit retains partial output and fails the case; destroyed path finalizes promptly with the destroyed note; SIGTERM during the finalization window still wins with 143 and no false success; the clean-control case is unchanged green.

### Platform finding recorded with the implementation (JDK 21, macOS)

The acceptance cases are built around measured JVM behavior, verified against the JDK 21.0.12.1 LTS source (`ProcessImpl.java`, extracted from `/Library/Java/JavaVirtualMachines/jdk-21.jdk/Contents/Home/lib/src.zip`):

- `destroy(boolean)` → `destroyForcibly()` closes stdin/stdout/stderr synchronously in the calling thread (JDK 21 lines 460–480). On the destroy path the capture stream therefore always EOFs promptly, and the natural-exit cutoff note is unreachable there on this platform; the destroyed note covers it. The cutoff note is retained in the generated code because it is correct on platforms/runtimes where destroy does not close the capture synchronously, and the case logic is portable.
- Natural-exit close runs in `processExited()` (line 596) under `synchronized` on the capture-stream monitor, which the parked reader holds inside its blocking read. When the pipe is empty and the reader is parked on `read()`, the hold is deterministic — which is what makes case A reliable without any output flooding. Conversely, any fixture that keeps data flowing (`yes`, prefill) makes the reader actively drain and EOF deterministically at close; flood-style fixtures were therefore falsified and abandoned (probe iterations retained only in session scratch, not in the repo).
- The fixture consequently uses a silent holder: a detached `sh -c "…; sleep N; echo late-grandchild-line" &` grandchild that keeps the pipe open without writing, plus up to 3 attempt retries per case to absorb residual scheduling variance. Attempt diagnostics go to stderr; assertions use plain Boolean `assertTrue` (zio-test `assertTrue` is Boolean-only; string-message overloads do not compile).

## Limitations / blockers

- The destroyed-path cutoff note is unreachable on JDK 21 macOS (destroy closes the capture synchronously; JDK source cited above). The note and its case logic are retained as platform-portable code; case B asserts prompt finalization and the destroyed note instead of the cutoff note. If another platform's JVM keeps the capture open through destroy, case B's assertions still hold; only the note text differs.
- The deterministic natural-exit hold relies on the JDK stream-monitor behavior documented above; it is verified on JDK 21.0.12.1 LTS (the project's gate toolchain). A JDK that changes `processExited()` locking could require fixture retuning; the 3-attempt retry loops are the bounded hedge, not a threshold relaxation.
- The 65,536-byte capture cap is pre-existing RAI-186 behavior and was not widened; RAI-216 only bounds time, not bytes.
- Lane evidence applies to this lane tip; per policy, final acceptance applies to the integrated candidate after coordinator merge.
