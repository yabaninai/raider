## Resulting behavior

`contracts/acceptance/cross-ecosystem/README.md` (new) documents the pinned
closure contract and the slf4j-api pin-maintenance note for the langchain4j
consumer:

- what the pin is load-bearing for: `dev.langchain4j` binds
  `org.slf4j.LoggerFactory` statically at first framework touch, so the
  requirement is a **run-time** classpath requirement, invisible to
  `compile_all` (its guard only checks non-empty output directories);
- what breaks when the pin drifts, with the concrete failure signature
  verbatim from a controlled drift probe (below): `javac` succeeds without
  the jar (exit 0), and the first `UserMessage` construction dies with
  `java.lang.NoClassDefFoundError: org/slf4j/LoggerFactory` at
  `dev.langchain4j.internal.Utils.<clinit>` (exit 1);
- how to re-pin on a consumer upgrade: re-derive the closure, update
  `consumer-deps.json` (`path`/`sha256`/`size`), update the `lib.sh`
  classpath lines, verify with the embedded snippet (must report
  `0 drifted/missing`), and run the full corpus — a re-pin is not proven by
  `compile_all` alone;
- the two-version situation: `org.slf4j:slf4j-api:2.0.17` is the load-bearing
  pin (`L4J_DEPS`); `2.0.18` is pinned in the contract but referenced by no
  driver classpath today.

The README includes a verification snippet over `consumer-deps.json`
(python3, stdlib only; checks key consistency, jar existence, sha256, size,
exits nonzero on drift). It runs clean on the current tree: 31 pins checked,
