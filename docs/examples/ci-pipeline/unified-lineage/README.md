# Unified lineage program for the billing pipeline shape (real generated artifact)

`lineage.scala` in this directory is the rendered unified multi-job lineage
program for the BillingCi pipeline shape (baseline-check → repair →
final-check → reviews → boundary). It is a REAL generated artifact of the
shipped projection, not an illustrative sketch.

## What it is and what it is not

- Per ADR-031, the program is a typed DRY-RUN description: executing it
  dispatches no model call, no tool call, and no I/O — it only reports the
  recorded call-graph structure. It is NOT a replay or rerun entrypoint.
- It is NOT an artifact of a live BillingCi execution. The BillingCi
  application launches its six stages as independent headless invocations, so
  each native run writes its own single-root lineage graph
  (see [`../successful-run.json`](../successful-run.json) for the actual
  captured six-root pipeline). This artifact demonstrates what Raider's
  lineage layer assembles when the same stages run as delegate children of
  ONE run and join one events stream.

## Current product wiring (reported accurately)

- The run artifact writer
  (`modules/cli/src/main/scala/raider/cli/run/RunLineageArtifacts.scala`)
  refuses phase-bearing graphs typed, so a unified program like this one is
  produced through the projection/verifier path — it is not yet written
  beside a run's `events.jsonl`.
- The product runtime cannot emit v2 phase envelopes yet; in the corpus the
  five phases are wire-native payloads of the frozen stream, authored through
  the real codecs (see the corpus README's construction rules and the RAI-145
  record's phase stand-in disclosure).
- The headless product path does not yet wire delegation into the `coder`
  agent; the join itself (`raider.cli.run.MultiJobExport`, RAI-144) is wired
  in the runner and exercised end to end by the fixtures.
