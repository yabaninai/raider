ЦЕЛЬ, ПОСЛЕ КОТОРОЙ МОЖНО ЗАЯВИТЬ О РЕЗУЛЬТАТЕ
Собранный и устанавливаемый Raider проходит W01–W17 из working-product.md на одной версии: native model→read/search→create/edit/delete→exec/check→исправление по failure→verified result; оба direct protocols; собственные sync/async subagents; history/sessions/context; настоящий REPL; typed DSL; CI runner/artifacts; custom tool/profile через public SPI.
OpenAI-compatible Chat и Anthropic-compatible Messages — самостоятельные transports. Yabanin optional; root/scopes/tools/DSL не зависят от gateway. OpenCode/pi backend bridge не подменяет собственный native loop.
M0/RAI-026 — промежуточная вертикальная приёмка. Working target также требует journal, instructions/context/compaction, sessions, typed tools/minimal SPI, clean package/help/examples и real task corpus. Не останавливаться на M0, stub SDK, console echo или зелёном mock transcript.
Базовый Yabanin profile/config/header/wrapper-owner/no-fallback contract W17 обязателен в offline acceptance; optional только запуск через него, enriched accounting/live stand/companion Go PR.
Отдельно отражай engineering_ready, live_verified и opencode_comparison. Live status веди per profile: direct-chat, direct-anthropic, gateway; один успешный endpoint не подтверждает остальные. При configured endpoint и ранее заданном owner cap выполняй live coding smoke и сравнение на одинаковых task/model/tool/budget условиях. Без этого не пиши «не хуже OpenCode»; заверши все независимые инженерные задачи и честно обозначь конкретный внешний blocker.

ПЕРВЫЕ ДЕЙСТВИЯ

Закрой актуальные findings RAI-001/SPIKE-OAI-01 узкими карточками: propagate producer exit через tee, fresh classes/run dirs, полный source/check manifest, test-owned TERM/JVM home/history, false-green fault injection. 2. Не переносить spike HTTP/blocking-read/cancel и headless error-exit/process-group claims в production без отрицательных fixtures. Перепроверь before-headers/stalled-body cancellation, actual child+grandchild cleanup, error/report-write exits. В OpenAI spike отдельно проверь malformed SSE/premature EOF, отсутствие complete tool round и hardcoded /v1 prefix; line-boundary cancel не гарантирует deadline. Dummy-key argv не переносить в production credential setup. Если sandbox не даёт тест, он unavailable, а не pass.
3. RAI-003 build/toolchain/JDK21, RAI-002 frozen public compile/schema contracts, RAI-004 stage-aware runner/testkit и ранний minimal development CI slice. Сначала проверь prerequisites и actual toolchain; не придумывай успешные команды.
4. Проверь python3 scripts/plan/validate.py; этот validator подтверждает только пакет документов. Полноценные runtime/CI/REPL gates требуется создать и выполнить.
5. Сохрани board с готовыми assignments и evidence. Не оставляй «ready, но ждёт dependency»: implementation prerequisites должны действительно быть готовы.

ОБЯЗАТЕЛЬНАЯ ПАРАЛЛЕЛЬНОСТЬ
Ты coordinator + до 3 активных workers суммарно; reviewer занимает свободный слот. Назначай независимые ready задачи сразу, не делай всё последовательно по номеру карточки. Следи за CPU/RAM/build contention; cap можно уменьшить при доказанной причине.
Каждый writer работает в отдельном worktree или отдельной копии immutable source snapshot; общий root checkout меняешь только ты. Перед dispatch сохрани абсолютный lane path, baseline hash, actual cwd, concrete allowed paths и frozen signatures. Child session сама по себе не worktree.
Если Git unborn/.git read-only/нужны uncommitted source: snapshot fallback из parallel-development.md. Включи нужные untracked исходники, исключи secrets/.git/output/cache, не используй mutable hardlinks. Не создавай initial commit из чужих файлов ради обхода ограничения и не делай stash/reset.
Snapshot без .git: worker пишет Git unavailable: isolated snapshot и проверяет baseline manifest. Quality runner обязан иметь manifest-diff mode (целевой QUALITY_BASE_MANIFEST) с тем же classifier/active gates, включая add/delete/mode/symlink. До его реализации — явные scoped bootstrap checks+inventory; не использовать отсутствующий flag и не переходить в root ради git status.
Если tool child cwd нельзя закрепить, используй поддерживаемый установленной версией отдельный OpenCode run --dir lane либо иной проверенный isolation mechanism. Не выдумывай API fields. Текущие permissions/model/account наследуй, не обходи через --auto. Если isolation недоступна, writers временно sequential, review/research parallel с объяснённой причиной.
Workers не запускают сборки одного checkout одновременно. Отдельные outputs/temp dirs/ports; mutable shared dependency cache только с подтверждённой lock/concurrency semantics. Все процессы разработки учтены и завершаются/возобновляются через coordinator.

OWNERSHIP И ИНТЕГРАЦИЯ
Только coordinator или эксклюзивно назначенный owner меняет public core contracts, build.sbt/project, shared HTTP framing, gate registry/thresholds, dependency graph и центральный board. Другие workers присылают bounded contract-change request с reproducer.
В packet worker: task+parent ID, absolute workspace, baseline, implementationDependencies/integrationDependencies, precise files/symbols/signatures, normal/error/cancel fixtures, active gates, deliverable и escalation condition. Большую карточку разбей на .a/.b/.c до coding, сохрани parent acceptance; разрешённая работа одной модели обычно 1–3 production files/один behavior.
Frozen ModelBackend/Tool contracts позволяют писать providers/tools против testkit одновременно с native runtime. Parent принимается лишь после integrationDependencies. Dependency refinement явно регистрируй и отдавай fresh reviewer; не молча обходи prerequisite.
Worker отдаёт patch+add/modify/delete inventory, before/after hashes, actual argv/exits/logs, remaining failures. Ты проверяешь allowed paths/base hashes, получаешь independent review и интегрируешь последовательно. Не копируй всю lane поверх root; конфликт merge/rebase с повтором tests.
После каждого integration batch shared compile/contracts+affected active gates. После каждой wave один runnable demo на общем дереве. Финальный milestone — новый общий прогон одной immutable сборки, а не сумма reports из несовместимых worktrees.
Автоматически назначай reviewer в свежем контексте после готовности diff. Reviewer проверяет код/fixtures/logs, не summary автора; автор не принимает себя. Не зависай на «жду независимого review», если сам можешь запустить reviewer. Если инструмент недоступен, зафиксируй pending и продолжай независимые ready задачи.

КАЧЕСТВО БЕЗ ЛОЖНОГО GREEN
Gate registry обязан различать bootstrap/component/milestone/release. Не требуй packaged REPL от facade card до compiler adapter и full CI от process-tool card до runner. Component acceptance проверяет уже реализуемые named cases; обязательства milestone остаются not_due/pending с владельцем и target stage. Это не passed/skipped-green.
make quality-full и acceptance-working на целевом milestone требуют все обязательные gates; missing/unavailable/timeout/scanner-error/stale/nonzero — fail/incomplete. Пустая suite не считается реализованной. Thresholds/protected verifiers не ослаблять; registry changes проходят отдельный fresh review.
До runner выполняй actual bootstrap commands и записывай versions/argv/exits. После runner: make quality-changed, make quality-changed QUALITY_EXECUTE=1, required profiles/stage и evidence validation. Новые flags/commands сначала реализовать и проверить, потом использовать в отчёте.
Evidence привязано к product input snapshot. Operational board/records исключаются только точным reviewed allowlist и имеют отдельный audit hash; code/spec/prompt/build/registry/fixtures не исключаются. Старое evidence не перепривязывается к новым source hashes. Проверяй stderr/exit и machine-readable results, а не фразу PASS модели.
Behavioural tests проверяют наблюдаемое поведение, не просто наличие класса. Для bug — сначала reproduction; для новой функции — contract fixture. Отдельно проверяй failure paths и fault injection, чтобы harness сам не делал green при ошибке.

НЕПОДВИЖНЫЕ RUNTIME/DSL КОНТРАКТЫ
Program.apply(input) создаёт lazy Task; imports/printing/construction не dispatch. ask foreground; start background; await ждёт existing job без повторной работы; send даёт receipt; cancel owned subtree. Один interpreter, никакого hidden global launch или fake Scala parser.
Сохрани короткие andThen/all/batch/scope/fork/join, typed heterogeneous tuples, compile-negative tests. Реальный REPL с val/def/case class/multiline/completion; bindings переживают ошибки; background output не портит ввод. Тот же definition file → :load и compile/run --bundle.
Обычная задача доступна сразу через configured worker/scout; headless run --agent также использует общий Runner. Пользователь не пишет for-workflow для каждого исправления бага.
ModelBackend = один inference attempt; AgentBackend = native/внешний agent loop. Наблюдаемые tools внешнего engine не исполняются второй раз native loop.
Cancellation-safe registration, one terminal result, bounded queues/cleanup; waiting parent не держит model permit (обязательный maxLLM=1 test). Tool args complete+validated до dispatch. Child capabilities только сужаются. Parallel writers продукта isolated или сериализованы.
Exact budget arithmetic; unknown/unpriced не zero; retries/repair accounted. Direct обоих wires без YABANIN_*; no forced /models support; Anthropic blocks/tool IDs/cumulative usage сохраняются. Required gateway deny не обходит direct provider.
Protected checks реально исполняются вне mutable agent workspace. CI noTTY/closed stdin/SIGTERM/exit/artifacts; artifact failure nonzero. Uncertain mutation не replay. Untrusted repository execution требует объявленной isolation capability; env filtering не OS sandbox.

TASK ACCEPTANCE И MODEL QUALITY
Минимум шесть настоящих fixture repositories/tasks: planted-bug review, regression fix, new file/module, refactor, multi-file patch, research report. Скриптованные HTTP ответы нужны для детерминированного protocol/runtime теста; production путь обязан обращаться к configured model.
Проверяй actual file diffs, hidden assertions, execution logs и test failure→repair→pass. Agent output «тесты прошли» без check receipt не success. Same build для REPL/CI/CLI с обоими provider adapters.
При разрешённом live comparison pin OpenCode/Raider/model/config, одинаковые задачи/budgets/tools, минимум 3 repetitions/task, одинаковый внешний verifier; сохраняй все результаты, cost uncertainty и failures. Слабость Raider превращай в regression task, а не смену rubric.

ЛИМИТЫ И ПРОДОЛЖЕНИЕ
Не меняй соседний Yabanin checkout, не делай push/deploy/release publish без отдельного назначения. Product paid inference только с заданным endpoint/account/cap; выбранная coding-модель OpenCode — текущий development context. Не показывай secrets в argv/history/logs/evidence.
Две содержательные неудачи с одной причиной → bounded reproducer+fresh design review; не повторяй одинаковую попытку бесконечно и не переписывай весь проект. Продолжай независимую работу при локальном blocker.
Не спрашивай «продолжать?» после каждой карточки и не заканчивай после spawn агентов. Следи за workers, интегрируй и веди next-ready queue до working acceptance или исчерпания реально доступной работы.
Перед context/turn limit сохрани active lane paths/baselines/session IDs, applied patches, exact checks/review, blocker и next executable command. Следующий turn продолжает board; не повторяет принятые задачи и не создаёт дублирующие workers.
